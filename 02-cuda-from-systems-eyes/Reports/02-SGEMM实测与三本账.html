一、三句话↑

这批数据最该记住的三件事

① 教科书那本账失效五次。 roofline 达成率超过 100%，说明 kernel 不在带宽墙上。 七个 kernel 里有五个超过 100%，K2 达到 2112.7%。 预测得准的是条数账，外推误差在 ±10% 以内。

② 收益最大的两步，算术强度都没变。 K1→K2 快 8.21×，只改了访存合并； K3→K4 快 3.36×，只改了指令条数。 K3c 的算术强度是 K3 的 1.6 倍，却只快 1.08×。

③ cuBLAS 自己也只达到峰值的 69.32%。 在 Ada 上，NVIDIA 重点优化的是 FP16/TF32，不是纯 FP32 的 SGEMM。 所以 cuBLAS 这个目标比想象中近：它只比 K6 快 1.40 倍。

二、cuBLAS 这个分母怎么定的↑

K0 = 2.401 ms / 57242.4 GFLOP/s / 占峰值 69.32%，抽样校验通过。 两项设置让它只跑纯 FP32：源码里设 cublasSetMathMode(CUBLAS_PEDANTIC_MATH)，环境变量设 NVIDIA_TF32_OVERRIDE=0。 如果 TF32 没禁掉，tensor core 会让结果超过 FP32 峰值。所以 69.32% 只可能是纯 FP32 的成绩。 

// cuBLAS 是列主序，而我们的矩阵是行主序。不想转置数据，就转置运算：
//   行主序的 C = A·B   等价于   列主序的 Cᵀ = Bᵀ·Aᵀ
cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N,
            N, M, K, &alpha,
            B, N,          // ← B 在前
            A, K, &beta,   // ← A 在后
            C, N);

恒等式和那行调用的关系，要从一个事实讲起： 同一段字节，按行主序读和按列主序读，得到的矩阵互为转置。 所以这里的"转置"不是一个操作。

指针不变，cuBLAS 读到的矩阵自动带了转置
缓冲区我们按行主序存的cuBLAS 按列主序读到的
AM × K 的 A K × M 的 Aᵀ
BK × N 的 B N × K 的 Bᵀ
CM × N 的 C N × M 的 Cᵀ

所以恒等式可以直接当参数表读： 

             Cᵀ    =    Bᵀ    ·    Aᵀ
             ↓          ↓          ↓
        写进 C 缓冲区  传 B 指针   传 A 指针

// 右边从左往右念一遍 —— Bᵀ 在前、Aᵀ 在后 —— 就是参数的先后顺序。
// 而 Bᵀ 和 Aᵀ 根本不用构造：把 B、A 的指针原样递过去，
// cuBLAS 用列主序一读，看到的就已经是 Bᵀ 和 Aᵀ 了。

维度和 ld 也自动对上。 cublasSgemm(h, …, m, n, k, …) 算的是 (m×k) · (k×n)。这里的结果是 N×M 的 Cᵀ， 所以 m=N, n=M，中间那一维仍是 k=K。 参数顺序 N, M, K 就是这样来的。 

参数            值      为什么
─────────────────────────────────────────────────────────
m               N       结果 Cᵀ 是 N×M，它的行数是 N
n               M       Cᵀ 的列数是 M
k               K       中间那一维没动
第一个矩阵       B       cuBLAS 读成 Bᵀ（N×K），正好是 m×k ✓
它的 ld         N       Bᵀ 在列主序下有 N 行 → ld = N
第二个矩阵       A       cuBLAS 读成 Aᵀ（K×M），正好是 k×n ✓
它的 ld         K       Aᵀ 有 K 行 → ld = K
输出            C       cuBLAS 写进去一个 N×M 的列主序矩阵
它的 ld         N       同上

// 最后一步：cuBLAS 往 C 缓冲区里写的是列主序的 Cᵀ（N×M）；
// 我们回过头按行主序去读同一段字节，看到的就是 M×N 的 C。闭环。

一句话记法

行主序的代码调用列主序的库时，把两个输入矩阵的顺序对调、 m 和 n 对调，其余不变。 代价为零：不多占显存，不多启动 kernel， 不多搬一次数据。 如果在这里真的调用一次 transpose，就白白多搬了两遍矩阵。 对 4096² 的 A 和 B，这是 256 MiB 的无谓读写（每个矩阵 64 MiB，转置要读一遍、写一遍）。

方法怎么测才算数↑

一、六条规矩↑

规矩为什么
八个 kernel 编进同一个可执行文件 "K6 是 cuBLAS 的百分之多少"这类比值，只在同一个二进制、同一次开机下成立。 实测：跨批次的绝对耗时漂 2–3%，同批内的比值只漂 0.5%。
kernel 顺序每轮轮转 避免热漂移总是拖慢排在最后的 kernel。
CUDA event 计时，取中位数 kernel 是异步下发的，主机计时器量不到。 用中位数而不用平均数：一次偶发卡顿就会把平均数带偏。
预热按 ITERS 分档，至少 1 次 cuBLAS 第一次调用要惰性加载 kernel 库， 一次要几十毫秒。 这个问题实际出现过：K0 在 512 上报出过 55 ms。
先校验再看速度 每个 kernel 抽 100 个元素，和 CPU 参照结果比对。 没验证过的"快"，通常是编译器把循环删掉了。
设备参数现读现用 峰值算力和带宽都从 cudaDeviceProp 读，不抄规格表。 这和 01 阶段"KV 池必须每台机器现读日志"是同一条原则。

二、两个口径，必须一起换↑

FP32 峰值   128 SM × 128 core × 2 × 2.52 GHz  = 82,575 GFLOP/s   // 设备自报的 clockRate ← 主表用这个
            128 SM × 128 core × 2 × 2.64 GHz = 86,508 GFLOP/s   // 本批 1 Hz 采样的中位数（稳态 2625–2655）

显存带宽    10501 MHz × 2（DDR 双沿）× 384 bit ÷ 8 = 1008 GB/s

主表的"占 FP32 峰值"按 2.52 GHz 那一行算。 这个时钟来自 cudaDeviceProp，换一台 4090 也读到同一个数。

标称值的意思是"保证不低于"。实际频率由 GPU Boost 按功耗墙（450 W）和温度动态调整，本批稳定在 2640 MHz。 上限是 3105，但稠密 FP32 GEMM 功耗太高，达不到。 要按实测口径引用，把整列乘 0.955（K6 从 49.57% 变成 47.32%）。 换口径时，分子和分母要一起换。 这个时钟每台机器不同，不能跨批次沿用。

"占 cuBLAS"那一列不受口径影响： 分子和分母都是 GFLOP/s，峰值约掉了。 所以"K6 = cuBLAS 的 71.5%" 在哪套口径下都成立，这也是本报告把它当主结论的原因。

推导八个指标各自怎么算出来的↑

本节是整份报告的核心：八个指标里只有耗时是量出来的，其余七个都从代码数出来。 数完再和实测对账，对上了才说明理解是对的。

一、一个 warp 读 shared memory 有两种姿势↑

一条 load 是整个 warp 的指令，它的代价由 32 个地址的分布决定。 32 个线程同时执行这条指令，各自把自己的 tx 代进下标，算出一个地址。 所以"一条 load"实际上是 32 个地址。

类型代码长什么样32 个地址硬件怎么做本批实测单价
广播 下标里没有 tx全部相同 取一次 4 字节，复制给全 warp 0.53 周期
32 路 下标里 tx 的系数是 132 个连号地址 落在 32 个不同 bank，一拍全服务完 2.69 周期
撞 bank tx 的系数是 s（≥ 2）只用到 1/s 的 bank 拆成 s 拍（例如系数 4：1/4 的 bank、4 拍） 更贵（本链未出现）
 判定方法：看下标里 tx 前面乘了什么。 没有 tx 是广播；系数是 1 是无冲突的 32 路；系数 ≥ 2 会撞 bank。 32 路的单价是广播的 2.69 ÷ 0.53 ≈ 5 倍。 K4 比 K3 快 3.36 倍，全部来自这个差价。

二、主例 K3：从代码一步步数出全部八个↑

K3 的内层循环只有两行，八个指标全从这两行数出来： 

for (int k = 0; k < TILE; ++k)
    acc += Mds[ty][k] * Nds[k][tx];
//         ↑ 下标没有 tx       ↑ 下标含 tx 且系数为 1
//           = 广播               = 32 路

第 1 步 · dist（32 路条数 ÷ FMA）

循环体里含 tx 的 shared 读：Nds[k][tx] —— 1 条
一次循环做几个 FMA：       1 个

dist = 1 条 ÷ 1 个 FMA = 1.000

除以 FMA 数，是为了把不同 kernel 放到同一把尺子上。 不同 kernel 一次循环做的 FMA 个数不同 （K3 做 1 个，K5 做 32 个）。除以之后，指标的含义统一为 "每做一次乘加，平均要发几条这类 load"。 这个商没有量纲，可以横向比较，这是"条数账"成立的前提。

第 2 步 · bcast（广播条数 ÷ FMA）

循环体里不含 tx 的 shared 读：Mds[ty][k] —— 1 条
bcast = 1 条 ÷ 1 个 FMA = 1.000

第 3 步 · ldg（全局 load 条数 ÷ FMA）

一个阶段里，每个线程从 global 搬 2 个元素进 shared（A 一个、B 一个）—— 2 条 LDG
同一个阶段里，内层循环跑 TILE = 32 步，每步 1 个 FMA        —— 32 个 FMA

ldg = 2 条 ÷ 32 个 FMA = 0.062

这 2 条为什么能摊给 32 个 FMA

因为搬进 shared memory 的数据被整个 block 复用。 一个线程只搬 2 个元素，但内层 32 步用到的是 32 个线程一起搬来的整行/整列。"我搬一个，我用三十二个"， 这句话就是 tiling 的全部。

三步合起来：load/FMA = dist + bcast + ldg = 1.000 + 1.000 + 0.062 = 2.062。

第 4 步 · bytesPerOut（每个输出要过多少字节）

一个 block 算 32×32 = 1024 个输出，沿 K 走 N/32 = 128 个阶段
每个阶段搬进来：A 的 32×32 + B 的 32×32 = 2048 个 float = 8192 字节
128 个阶段合计：128 × 8192 = 1,048,576 字节
摊到 1024 个输出：1,048,576 ÷ 1024 = 1024 字节
再加上写回 C 自己那 4 字节：            1028 字节/输出

第 5 步 · 算术强度与 roofline 达成率

算术强度回答"这个 kernel 每搬一个字节，能换来多少次浮点运算"。 它把第 4 步的 bytesPerOut 换算成一个 和矩阵规模无关的比值，所以不同 kernel 可以直接比较。 

算术强度 = 每个输出的浮点运算 ÷ 每个输出的字节
         = 2K ÷ bytesPerOut
         = 2×4096 ÷ 1028 = 7.969 FLOP/byte

// 分子的 2K：C 的每个元素要做 K 次乘加，一次乘加算 2 个浮点运算（1 乘 1 加）。
// 分母的 1028：第 4 步数出来的，每个输出摊到的显存字节。

roofline 上限 = 算术强度 × 峰值带宽
             = 7.969 × 1008 = 8033 GFLOP/s

// 意思是：如果这个 kernel 把显存带宽跑满，它最快只能到 8033。
// 1008 GB/s 是 4090 的理论峰值带宽，口径见 §2·二。

下面的 6184.0 是「实测吞吐」，是八步里唯一一个量出来的数； 其余七个都从代码数出来。 所以下面把它单独拆开。 

实测 GFLOP/s = 2·M·N·K ÷ 耗时(秒) ÷ 1e9

// ① M·N·K 是这次乘法一共要做多少次乘加（FMA）
//    C 有 M×N 个元素，每个元素要沿 K 方向累加 K 次
   M·N·K = 4096 × 4096 × 4096 = 68,719,476,736 次 FMA

// ② 乘以 2：一次 FMA 在 FLOP 的记法里算 2 个运算（1 次乘 + 1 次加）
//    这是整个行业的统一口径 —— cuBLAS、Nsight、论文都这么算，
//    否则跟别人的数字没法比
   2 × 68,719,476,736 = 137,438,953,472 FLOP ≈ 137.44 GFLOP

// ③ 除以耗时。22.225 ms 就是主表里那个中位耗时 ——
//    和第 6 步算节拍用的是【同一个数】，同一次测量，没有第二次计时
   137,438,953,472 ÷ 0.022225 s = 6,183,979,908,751 FLOP/s

// ④ 换成 GFLOP/s（除以 1e9）
   6,183,979,908,751 ÷ 1e9 = 6184.0 GFLOP/s

达成率 = 实测 ÷ 上限 = 6184.0 ÷ 8033 = 77.0%

达成率是在检验一个假设，不是在打分

8033 是推出来的（从代码数字节 → 算算术强度 → 乘带宽）， 6184.0 是量出来的（跑三轮取中位数）。 分母的含义是：假如数出来的字节全部走显存， 而且带宽跑满，kernel 能跑多快。 达成率检验的就是这个"假如"。 结果分三档，不是两档：

≈ 100%  贴着屋顶   带宽真跑满了 —— 这才是"受带宽限制"，想更快只能提高算术强度
≪ 100%  离屋顶远   带宽没跑满 → 瓶颈不是带宽，在别处（指令吞吐 / 延迟 / 占用率）
> 100%  超出屋顶   分母错了 —— 字节没全走显存，命中了 L2。模型在这里被证伪

⚠ "达成率低"不等于"受带宽限制"。 对同一个 kernel，分母是常数， 达成率只是换了刻度的速度：跑得慢，达成率就低。 但"慢"本身说明不了"慢在哪"。

K3 的 77.0% 没超过 100%，所以字节账在 K3 上没有被证伪，但这不等于字节账成立。 K2 的 2112.7% 才是直接证伪。 

K1 257.4%   K2 2112.7%   K3 77.0%   K3c 52.2%   K4 258.6%   K5 269.1%   K6 319.2%

// 七个里没有一个贴近 100% —— 最近的就是 K3 的 77.0%。
// 也就是说：这条链上没有一个 kernel 真的受带宽限制。
// 五个被直接证伪；K3/K3c 虽然没被证伪，但离屋顶太远，同样说明带宽不是它们的墙。

K3 真正的瓶颈是指令条数。 第 8 步用条数账算出 3.340，和实测 3.34 一致； §4 再把七个 kernel 并排对比。

第 6 步 · 节拍（把实测耗时换算成周期）

节拍 = 32 × SM数 × 时钟 × 耗时(秒) ÷ (M·N·K)
     = 32 × 128 × 2.52e9 × 22.225e-3 ÷ 4096³
     = 3.338 周期/warp圈        （程序打印 3.34）

这个公式在算什么

分母 M·N·K 是这次乘法一共要做的 FMA 个数。 除以 32，得到要跑多少个 warp 圈。 一圈指一个 warp 的 32 个线程各做一次 FMA。

分子 SM数 × 时钟 × 耗时 是这段时间里全卡一共经过多少 SM-周期。

两者相除，得到每个 warp 圈平均占用多少 SM-周期。数值越小越快。 4090 上的物理地板是 0.25， 因为每个 SM 每周期能发 128 个 FP32 FMA，即 4 个 warp 圈。 K6 实测 0.50，是地板的 2 倍。

第 7 步 · 每条 load 多少周期

每条 load 周期 = 节拍 ÷ load/FMA = 3.34 ÷ 2.062 = 1.62

这是诊断量，不是预测量。 它把"这个 kernel 慢"换成"它每发一条 load 要付几个周期"。 如果这个数在 kernel 之间差很多，说明 load 的类型构成变了。 例如 K1 是 15.91：它每个 FMA 的两条 load 一共触发 33 个请求（A 32 个、B 1 个）。

第 8 步 · 模型预测

预测节拍 = 2.69 × dist + 0.53 × bcast + 1.94 × ldg
        = 2.69 × 1.000 + 0.53 × 1.000 + 1.94 × 0.062
        = 3.340        实测 3.34   ✓

K3 是标定点之一，所以这里必然吻合。 真正的检验是用同样三个单价外推 K3c 和 K5，见 §3 · 六。

三、K1 / K2：没有 shared memory 的特例，以及为什么需要请求账↑

下面按 K1 → K2 → K3c → K4 → K5 → K6 的顺序补齐其余六个 kernel，每个都走同样的八步。 K3 是主例，上面已经逐步算过。 只有 K1/K2 多一步"请求账"，因为从 K3 起访存全部合并，这本账归零，不再变化。

K1 · 九步

const int x = blockIdx.x * blockDim.x + threadIdx.x;   // 行 ← 从 .x 来
const int y = blockIdx.y * blockDim.y + threadIdx.y;   // 列 ← 从 .y 来
float acc = 0.0f;
for (int i = 0; i < K; ++i)
    acc += A[x * K + i] * B[i * N + y];                // ← 1 个 FMA + 2 条 LDG（全局！）
C[x * N + y] = alpha * acc + beta * C[x * N + y];
第 1 步  这个线程负责几个输出？
  一个 acc → 1 个输出                              // 和 K3 相同

第 2 步  内层每轮：几个 FMA、几条 shared load、各属哪类？
  acc += A[x * K + i] * B[i * N + y];
        └─ 1 个 FMA ─┘  └ 2 条 LDG ┘                    // 是 LDG（全局），不是 LDS
  一条 shared load 都没有  →  dist  = 0 ÷ 1 = 0.000
                            bcast = 0 ÷ 1 = 0.000

第 3 步  全局 load 怎么摊到每个 FMA 上？

  →  ldg = 2 条 ÷ 1 个 FMA = 2.000

第 4 步  bytesPerOut：每个输出摊多少字节？

第 5 步  AI = 2K ÷ bytesPerOut

第 7 步  每条 load 周期

  // 换成"请求"当单位，数量级立刻就回来了。

四、K3c / K4：同叫"粗化"，动的却是两本不同的账↑

两个 kernel 都让一个线程多算几个输出，但省下来的东西完全不同。 判断方法是看多出来的输出摊薄了哪一项。

K3c · 每线程 4 个输出（同一行上，跨 4 个 tile）

float p0 = 0.0f, p1 = 0.0f, p2 = 0.0f, p3 = 0.0f;   // ← 4 个累加器 = 4 个输出
for (int ph = 0; ph < K / TILE; ++ph) {             // ← 128 个阶段
    Mds[ty][tx] = A[Row * K + aCol];                // ← M tile 每阶段只搬一次（1 格）
    for (int c = 0; c < COARSE; ++c) {              // ← 粗化循环，4 轮
        Nds[ty][tx] = B[bRow * N + col];            // ← N tile 随列变，4 格
        __syncthreads();
        for (int k = 0; k < TILE; ++k)
            acc += Mds[ty][k] * Nds[k][tx];         // ← 内层和 K3 一字不差！
        ...
    }
}
第 1 步  几个输出？
  p0…p3 四个累加器 → 4 个输出（同一行上，跨 4 个 tile）

第 2 步  内层每轮：几个 FMA、几条 LDS？
  acc += Mds[ty][k] * Nds[k][tx];       // 和 K3 一字不差
  1 个 FMA、2 条 LDS  →  dist = 1 ÷ 1 = 1.000   bcast = 1 ÷ 1 = 1.000
  ← 条数账一分没省，这是 K3c 的全部问题所在

第 3 步  全局 load 摊到每个 FMA？
  每阶段每线程搬 1 格 M + 4 格 N = 5 格
  每阶段做 4 个 c × 32 轮 = 128 个 FMA
  →  ldg = 5 ÷ 128 = 0.039                     // K3 是 0.062

第 4 步  bytesPerOut
  每阶段 5 格 ÷ 4 个输出 = 1.25 格/输出                 // K3 是 2 格
  128 阶段 × 1.25 × 4 字节 + 4 = 644 字节

  //   每线程 4 个输出 → 写回 4 格 = 16 字节 → 摊到每个输出仍是 4 字节。

第 5 步  AI
  8192 ÷ 644 = 12.720 FLOP/byte          // K3 是 7.969，提高 1.6 倍

  达成率 = 6690.6 ÷ 12823 = 52.2%     // AI 越高，这个百分比反而越低

  //     double gflops = 2.0 * M * N * K / (ms / 1000.0) / 1e9;
  //     = 2 × 4096³ ÷ 0.020542 s ÷ 1e9，即第 6 步那个耗时的另一种写法

第 6 步  节拍

第 7 步  每条 load 周期
  load/FMA = 1.000 + 1.000 + 0.039 = 2.039
  3.09 ÷ 2.039 ≈ 1.51 周期          // K3 是 1.62

第 8 步  模型预测
  2.69 × 1.000 + 0.53 × 1.000 + 1.94 × 0.039 = 3.295
  实测 3.09，误差 +6.6%   // 它没参与标定，这是一次外推

账面结论

K3c 的 AI 涨到 K3 的 1.6 倍（字节账大动），条数账 2.062 → 2.039（几乎没动），实测只快 1.08×。 把第 3、4 步的两行写成一个式子，就能看出粗化省了什么， 以及还剩多少可省。

每阶段、每个输出摊到的格数 = (1 + COARSE) ÷ COARSE
                              ↑       ↑
                        M 搬 1 格  N 搬 COARSE 格

  COARSE = 4：(1 + 4) ÷ 4 = 1.25 格        // K3 相当于 COARSE=1：(1+1)÷1 = 2 格

// 分子那个 1 就是粗化的全部收益：同一行上的 COARSE 个输出共用同一块 M tile，
// 每阶段只搬一次。不粗化的话（4 个独立的 K3 block），这一格要被各搬一次，共 4 次。
// N 那一侧省不掉 —— COARSE 个输出的列号各不相同，每人都得要自己那一格。

再加下去还剩多少？让 COARSE 一路涨：
  COARSE → ∞ 时 (1 + COARSE) ÷ COARSE → 1     // M 那 1 格被摊成 0，只剩 N 的 1 格
  bytesPerOut → 128 阶段 × 1 格 × 4 字节 + 4 = 516 字节
  AI 上限     → 8192 ÷ 516 = 15.876          // ≈ TILE ÷ 2 = 16

  COARSE = 4 已经拿到 12.720 = 上限的 80.1%

把 COARSE 从 4 加到无穷，AI 最多再涨约四分之一（15.876 ÷ 12.720 = 1.25）。 已经拿到的 1.6 倍 AI 只换来 1.08× 的速度， 因为字节账本来就不是这条链上的瓶颈。 所以 K5 没有继续压字节账，而是转去砍条数账。

三个结论

① 「优化了 63.1 倍」只在方阵上成立。（63.1 倍来自主表；下面的形状扫描是另一次运行，方阵测得 63.4 倍。）

方阵 4096³     K1 → K6   63.4×
prefill        K1 → K6   49.2×
decode b32     K1 → K6   23.8×
decode b1      K1 → K6   3.4×   ← 只剩零头

② decode 上 K6 反而比 K4 慢（0.95×）。 K6 比 K4 多出的改进全部用来砍指令条数，而 decode 撞的是带宽墙。 所以砍条数没用；M=1 时，更大的 tile 还会浪费更多线程。 这证实了"三本账只在算力受限一侧有效"。

③ decode 上我们几乎追平 cuBLAS，K4 还超过了它（102.6%）。 这和事前预测正好相反。原因是带宽墙对谁都一样高。 decode 的瓶颈是把 18944×3584 的权重完整读一遍，谁做都要付同样的读显存时间， cuBLAS 精巧的分块调度用不上。 cuBLAS 的优势只在算力受限一侧兑现：prefill 上它还保有方阵成绩的 96.7%，我们的 K6 只有 cuBLAS 的 57.1%。

给下一阶段的接口

cuBLAS   decode b1   M=1    0.302 ms   449.6 GFLOP/s
         decode b32  M=32   0.313 ms   13882.7 GFLOP/s

  活多了 32×（M 从 1 变成 32），耗时只多 1.04×
  →  实测吞吐比 = 13882.7 ÷ 449.6 = 30.9×        // = 32 ÷ 1.04

batch 32 和 batch 1 的耗时几乎相同，吞吐却是 batch 1 的 30.9 倍。 这是 continuous batching 必须存在的量化理由。 它也对上了 01 阶段在 vLLM 吞吐曲线上看到的宏观现象：那边是现象，这里是机制。 注意 30.9 不是 32： 耗时多出的那 1.04× 零头，正是"批到多大就开始付钱"的起点。

一、K1 的 211.911 ms 里，四分之三和"不合并"无关↑

回乘检验：2.392 × 3.432 = 8.209（3.43 是 3.432 四舍五入后的值）

N=4096 时，A 的行跨度恰好是 16384 字节 = 2¹⁴；N=4097 时变成 16388。 两次运行只改了这一个变量。 所以"合并访存是性价比最高的一步"要加注： 那 8.21 倍里，只有 2.392 倍来自合并本身，另外 3.43 倍来自顺带治好的跨度冲突。 对照组：同样从 4096 改到 4097，K2–K5 只慢 2.8%–7.1%，cuBLAS 慢 15.7%。K6 用 float4，要求 N 是 4 的倍数，所以测的是 4100，慢 7.5%。
