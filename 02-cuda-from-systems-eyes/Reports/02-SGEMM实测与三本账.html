一、三句话↑

这批数据最该被记住的三件事

① 教科书那本账失效五次。 roofline 达成率超过 100% 就意味着"它根本没在带宽墙上"—— 七个 kernel 里有五个超了，K2 甚至到 2113.5%。 而真正预测得准的是条数账，外推误差 ±10% 以内。

② 收益最大的两步，算术强度一个字都没变。 K1→K2（8.21×）和 K3→K4（3.36×）—— 前者只动了访存合并，后者只动了指令条数。 而算术强度真涨了 1.6 倍的 K3c，只换来 1.08×。

③ cuBLAS 自己也只有峰值的 69.66%。 纯 FP32 的 SGEMM 在 Ada 上并不是 NVIDIA 精心优化的路径（FP16/TF32 才是）， 所以"离 cuBLAS 还有多远"这个靶子比想象中近 —— 它只比 K6 快 1.40 倍。

二、cuBLAS 这个分母怎么定的↑

K0 = 2.401 ms / 57242.4 GFLOP/s / 占峰值 69.66%，抽样校验通过。 两道保险确保它是纯 FP32：源码里 cublasSetMathMode(CUBLAS_PEDANTIC_MATH)，环境里 NVIDIA_TF32_OVERRIDE=0。 如果 TF32 没禁掉，tensor core 会把数字顶到 FP32 峰值以上 —— 69.66% 这个位置只可能是纯 FP32 在跑。 

// cuBLAS 是列主序，而我们的矩阵是行主序。不想转置数据，就转置运算：
//   行主序的 C = A·B   等价于   列主序的 Cᵀ = Bᵀ·Aᵀ
// 所以把 B 当第一个参数、A 当第二个传进去，m/n 也跟着换位置。
cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N,
            N, M, K, &alpha,
            B, N,          // ← B 在前
            A, K, &beta,   // ← A 在后
            C, N);

方法怎么测才算数↑

一、六条规矩↑

规矩为什么
八个 kernel 进同一个可执行文件 "K6 是 cuBLAS 的百分之多少"这类比值，只有在同一个二进制、同一次开机下才成立。 实测：跨批次绝对耗时漂 2–3%，同批内比值只漂 0.5%
kernel 顺序每轮轮转 避免热漂移固定惩罚排在最后的那一个
CUDA event 计时，取中位数 kernel 是异步下发的，主机计时器量不到。 中位数而非平均：一次偶发卡顿会把平均整个带偏
预热按 ITERS 分档，至少 1 次 cuBLAS 第一次调用要惰性加载 kernel 库， 一次就是几十毫秒 —— 这个坑真踩过，K0 在 512 上报出过 55 ms
先校验再看速度 每个 kernel 抽 100 个元素和 CPU 参照比。 没验证过的"快"通常是编译器把循环删了
设备参数现读现用 峰值算力和带宽都从 cudaDeviceProp 取，不抄规格表。 和 01 阶段"KV 池必须每台机器现读日志"是同一条原则

二、两个口径，必须一起换↑

FP32 峰值   128 SM × 128 core × 2 × 2.52 GHz = 82,575 GFLOP/s   // 设备报告的 clockRate
            128 SM × 128 core × 2 × 2.713 GHz = 88,908 GFLOP/s   // 压测中实测的加速时钟

显存带宽    10501 MHz × 2（DDR 双沿）× 384 bit ÷ 8 = 1008 GB/s

主表的"占 FP32 峰值"按 2.52 GHz 算。 换成 2.713 GHz 的口径，K6 的 71.5% 那一列里 "占峰值"要从 50.08% 修正为 46.5%，cuBLAS 从 69.66% 修正为 64.4%。 两个要一起换，不能只换一个 —— 这是最容易出错的地方。 而"占 cuBLAS"那一列不受影响，因为分子分母同时变。

推导八个指标各自怎么算出来的↑

这一节是整份报告的核心。 八个指标里，只有一个（耗时）是量出来的，其余七个全部从代码数出来 —— 数完再和实测对账，对上了才说明理解是对的。

一、先看清一件事：一个 warp 读 shared 有两种姿势↑

一条 load 是整个 warp 的指令。 32 个线程同时执行它，各自把自己的 tx 代进下标算出一个地址 —— 所以"一条 load"其实是 32 个地址。这 32 个地址长什么样，决定了它便宜还是贵。

类型代码长什么样32 个地址硬件怎么做本批实测单价
广播 下标里没有 tx全部相同 取一次 4 字节，复制给全 warp 0.53 周期
32 路 下标里 tx 的系数是 132 个连号地址 落在 32 个不同 bank，一拍全服务完 2.69 周期
撞 bank tx 的系数 ≥ 2只用到 1/4 的 bank 拆成 4 拍 更贵（本链未出现）
 一眼判定法：看下标里 tx 前面乘了什么。 没有 tx 是广播，系数 1 是干净的 32 路，系数 ≥ 2 就开始撞 bank。 两者单价差 2.69 ÷ 0.53 ≈ 5 倍 —— 这是 K3→K4 那 3.36 倍的全部来源。

二、主例 K3：从代码一步步数出全部八个↑

K3 的内层循环就这么两行，八个指标全从它们数出来： 

for (int k = 0; k < TILE; ++k)
    acc += Mds[ty][k] * Nds[k][tx];
//         ↑ 下标没有 tx       ↑ 下标含 tx 且系数为 1
//           = 广播               = 32 路

第 1 步 · dist（32 路条数 ÷ FMA）

循环体里含 tx 的 shared 读：Nds[k][tx] —— 1 条
一次循环做几个 FMA：       1 个

dist = 1 条 ÷ 1 个 FMA = 1.000

为什么要除以 FMA 数？ 因为不同 kernel 的一次循环做的 FMA 个数不一样 （K3 做 1 个，K5 做 32 个）。除以 FMA 数就把它们归一到同一把尺子上： "每做一次乘加，平均要发多少条这类 load"。 这个商是无量纲的，可以横向比较 —— 这正是"条数账"能成立的前提。

第 2 步 · bcast（广播条数 ÷ FMA）

循环体里不含 tx 的 shared 读：Mds[ty][k] —— 1 条
bcast = 1 条 ÷ 1 个 FMA = 1.000

第 3 步 · ldg（全局 load 条数 ÷ FMA）

一个阶段里，每个线程从 global 搬 2 个元素进 shared（A 一个、B 一个）—— 2 条 LDG
同一个阶段里，内层循环跑 TILE = 32 步，每步 1 个 FMA        —— 32 个 FMA

ldg = 2 条 ÷ 32 个 FMA = 0.062

这 2 条为什么能摊给 32 个 FMA

因为搬进 shared 的东西被整个 block 复用了。 一个线程只搬 2 个元素，但内层 32 步用到的是 32 个线程一起搬来的那一整行/整列。"我搬一个，我用三十二个"—— 这一句就是 tiling 的全部。

三步合起来：load/FMA = dist + bcast + ldg = 1.000 + 1.000 + 0.062 = 2.062。

第 4 步 · bytesPerOut（每个输出要过多少字节）

一个 block 算 32×32 = 1024 个输出，沿 K 走 N/32 = 128 个阶段
每个阶段搬进来：A 的 32×32 + B 的 32×32 = 2048 个 float = 8192 字节
128 个阶段合计：128 × 8192 = 1,048,576 字节
摊到 1024 个输出：1,048,576 ÷ 1024 = 1024 字节
再加上写回 C 自己那 4 字节：            1028 字节/输出

第 5 步 · 算术强度与 roofline 达成率

算术强度 = 每个输出的浮点运算 ÷ 每个输出的字节
         = 2K ÷ bytesPerOut = 2×4096 ÷ 1028 = 7.969 FLOP/byte

roofline 上限 = 算术强度 × 峰值带宽 = 7.969 × 1008 = 8033 GFLOP/s

实测 GFLOP/s = 2·M·N·K ÷ 耗时(秒) ÷ 1e9
             = 2 × 4096³ ÷ (22.225/1000) ÷ 1e9 = 6184.0

达成率 = 6184.0 ÷ 8033 = 77.0%

K3 的达成率 77.0%，低于 100% —— 这是七个里少数几个"字节账还没失效"的。 而 K2 的达成率是 2113.5%，超了二十倍。

第 6 步 · 节拍（唯一用到实测值的一步）

节拍 = 32 × SM数 × 时钟 × 耗时(秒) ÷ (M·N·K)
     = 32 × 128 × 2.52e9 × 22.225e-3 ÷ 4096³
     = 3.338 周期/warp圈        （程序打印 3.34）

这个公式在算什么

分母 M·N·K 是这次乘法一共要做的 FMA 个数。 除以 32 得到"要跑多少个 warp 圈"—— 一圈指一个 warp 的 32 个线程各做一次 FMA。

分子 SM数 × 时钟 × 耗时 是这段时间里全卡一共转了多少 SM-周期。

两者相除 = 平均每个 warp 圈占掉多少 SM-周期。越小越快。 4090 上的物理地板是 0.25 —— 每个 SM 每周期能发 128 个 FP32 FMA，也就是 4 个 warp 圈。 K6 实测 0.50，是地板的 2 倍。

第 7 步 · 每条 load 多少周期

每条 load 周期 = 节拍 ÷ load/FMA = 3.34 ÷ 2.062 = 1.62

这是个诊断量，不是预测量。 它把"这个 kernel 慢"翻译成"它每发一条 load 要付多少周期"。 如果这个数在不同 kernel 之间差很多，说明 load 的类型构成变了 （比如 K1 的 15.88 —— 它那条 load 触发 33 个请求）。

第 8 步 · 模型预测

预测节拍 = 2.69 × dist + 0.53 × bcast + 1.94 × ldg
        = 2.69 × 1.000 + 0.53 × 1.000 + 1.94 × 0.062
        = 3.34        实测 3.34   ✓

K3 是标定点之一，所以这里必然吻合。 真正的考验是拿同样三个单价去外推 K3c 和 K5 —— 见 §3 · 六。

三、K1 / K2：没有 shared 的特例，以及请求账为什么必须存在↑

for (int i = 0; i < K; ++i)
    acc += A[row * K + i] * B[i * N + col];     // 两条都是全局 load

第 1 步 dist  = 0 条 shared ÷ 1 FMA = 0.000     // 根本没有 shared
第 2 步 bcast = 0 条 ÷ 1 FMA        = 0.000
第 3 步 ldg   = 2 条 ÷ 1 FMA        = 2.000     // 一个 FMA 配两条全局读
       load/FMA = 2.000
第 4 步 bytesPerOut = 2K×4 + 4 = 32,772 字节        // 完全没有复用
第 5 步 算术强度 = 2×4096 ÷ 32772 = 0.250
第 6 步 节拍     K1 31.76   K2 3.88          ← 差 8 倍
第 8 步 模型预测  两者都是 1.94 × 2.000 = 3.88  ← 完全相同

第三本账就是在这里诞生的

K1 和 K2 的前七步逐字相同：同样的算术强度、同样的 load/FMA、同样的模型预测。 可实测差了 8.21 倍。

后来的 SASS 反汇编给了决定性证据： K1 和 K2 的指令构成逐项完全相同 （都是 30 FFMA / 59 LDG.32 / 216 条总计）。 所以这 8.21 倍里，指令条数的贡献是严格的零。

差别只在一条指令触发几个内存事务： K1 每个 FMA 要 33 个请求 （A 的那条被拆成 32 个 + B 的 1 个），K2 只要 2 个。 条数账的误差 -88% —— 它不是模型错了，是这个 kernel 根本不在它的适用区间里。

四、K3c / K4：同叫"粗化"，动的是两本不同的账↑

// K3c：一个线程算 4 个输出，但 4 个输出【横向排开】
for (int c = 0; c < 4; ++c)
    for (int k = 0; k < TILE; ++k)
        acc[c] += Mds[ty][k] * Nds[c][k][tx];
// 每个 FMA 仍然要 1 条广播 + 1 条 32 路 —— 内层一条都没少
dist 12.720→ 1.000    bcast 1.000    ldg 0.062→0.039   // 只有 ldg 降了
省的是"搬进 shared"那一侧 —— 字节账，实测 1.08×

// K4：一个线程算 8 个输出，8 个输出【纵向排开】
float nv = Nds[k][tx];                 // ← 提出来！读一次
for (int r = 0; r < 8; ++r)
    acc[r] += Mds[ty*8+r][k] * nv;     // ← 用 8 次
// 8 个 FMA 只发 1 条 32 路 + 8 条广播
dist 1.000 → 0.125    bcast 1.000    ldg 0.062
省的是内层循环的指令条数 —— 条数账，实测 3.36×

两个都叫"线程粗化"，收益差了 28.8 倍。 区别就在那一行 float nv = ... —— 把贵的那类 load 提到循环外面。 K3c 的 4 个输出横向排开，各自要用 Nds 的不同列，提不出来； K4 的 8 个输出纵向排开，共用同一个 Nds 元素，才提得出来。

五、K5 / K6：两个方向一起复用，再换成 128 位↑

// K5：8 行 × 4 列 = 32 个输出
for (int r = 0; r < 8; ++r) m[r] = Ads[k][i0+r];      // 8 条广播
for (int c = 0; c < 4; ++c) n[c] = Bds[k][tx+c*32];   // 4 条 32 路
for (r) for (c) acc[r][c] += m[r] * n[c];             // 32 个 FMA

dist  = 4 条 ÷ 32 FMA = 0.125
bcast = 8 条 ÷ 32 FMA = 0.250      // 两个方向一起摊薄
ldg   = 0.039

// K6：把上面 12 条 32 位读换成 3 条 128 位读
float4 m01 = ((float4*)&Ads[k][i0])[0];   // 2 条广播覆盖 8 个 m
float4 m23 = ((float4*)&Ads[k][i0])[1];
float4 nv  = ((float4*)&Bds[k][tx*4])[0]; // 1 条 32 路覆盖 4 个 n

dist  = 1 条 ÷ 32 FMA = 0.031
bcast = 2 条 ÷ 32 FMA = 0.062
ldg   = 0.010       // 字节数一个没变，AI 仍是 12.720

K6 的模型预测为什么不准

预测 0.136，实测 0.50 —— 差 3.7 倍。

因为三个单价都是用 32 位 load 标定的，而 K6 用的是 128 位 load。 一条 128 位 load 搬 4 倍的数据，不可能和 32 位 load 同价。 反过来用实测反推：128 位的隐含倍率 = 0.50 ÷ 0.136 = 3.68 —— 接近 4 但不到，说明 128 位 load 确实比 4 条 32 位便宜，但省不到 4 倍。

SASS 又给这个数字打了个折扣

反汇编发现 K5 本来就有 64 条 LDS.128 —— 编译器自己把它三分之一的 shared load 向量化了。 所以手推的 "K5 全是标量" 这个前提是错的， K5 的 dist / bcast 被高估了。 真实的访存指令比是 264 ÷ 114 = 2.32 倍， 不是条数账说的 3.98 倍。 3.68 这个倍率里，混着这部分误差 —— 它是个上界，不是干净的单价。

外推验收：两个没参与标定的点

K3c 误差 +6.6%，K5 误差 -7.6% —— 都在 ±10% 以内。 这是条数账唯一能被证伪的地方：三个点定三个参数是必然吻合的， 只有外推到没参与标定的点，模型才算被检验过。 两个已知边界外的点（K1 的非合并、K6 的 128 位） 各缺一个参数，不算模型错。

二、那句该改写的话↑

原来的说法

"SGEMM 在 4090 上摸不到 FP32 峰值，因为 128×128 分块的算术强度只有 32， 而脊点是 82 —— 剩下的靠 L2 和寄存器复用补。"

实测之后应该这么说

"SGEMM 在 4090 上摸不到 FP32 峰值，不是因为带宽 —— K6 的 roofline 达成率 322%，说明它早就不在那堵墙上了。 真正的墙在 LSU：算力地板是 0.25 周期/warp圈， K6 实测 0.50，差的那一倍是 3 条 128 位 shared load 占掉的发射槽。 要再往上走，只能继续砍 load 条数（warptiling）或者换张量核心。"

1024 的 footprint 只有 12.6 MB，整个塞得进 4090 的 75.5 MB L2 —— 那种尺寸测的不是显存带宽。 4096（201 MB）起才明显超出 L2。 主表取 4096 是折中：够大到脱离 L2，又不至于让 K1 单次就要 1.6 秒。

8192 那一列有两件事值得看

① K6 的价值要到装不下 L2 的尺寸才显现。 4096 上它只值 1.19×，8192 上变成 1.73×。

② 只有 cuBLAS 在 8192 上不掉（1.03×），我们最好的 K6 掉到 0.87、K5 掉到 0.60。 差距就在 double buffering 和更好的 L2 复用策略上 —— 这比"占 cuBLAS 71.5%"更具体地说明了缺口在哪。

二、形状：换成真实推理负载还剩多少↑

三个结论

① 「优化了 63.1 倍」只在方阵上成立。

方阵 4096³     K1 → K6   63.4×
prefill        K1 → K6   49.2×
decode b32     K1 → K6   23.8×
decode b1      K1 → K6   3.4×   ← 只剩零头

② decode 上 K6 反而比 K4 慢（0.95×）。 K6 相对 K4 多出来的本事全部用来砍指令条数， 而 decode 那一侧的墙是带宽 —— 砍条数不但没用，更大的 tile 在 M=1 时还浪费更多线程。 这就把"三本账只在算力受限一侧有效"钉死了。

③ decode 上我们几乎追平 cuBLAS，K4 甚至超过它（102.6%）。 这和事前预测正好相反。原因不难想：带宽墙对谁都一样高。 decode 的瓶颈是把 18944×3584 的权重完整读一遍，这件事谁做都得付同样的 DRAM 时间， cuBLAS 那些精巧的分块调度无处施展。 cuBLAS 的优势只在算力受限那一侧兑现 —— prefill 上它还有 96.7%，我们的 K6 只剩 57.1%。

给下一阶段的接口

decode b1   0.302 ms        decode b32  0.313 ms        耗时比 1.04×
                                                       吞吐比 32×

batch 32 和 batch 1 花一样的时间，吞吐差 32 倍。 这就是 continuous batching 必须存在的量化理由 —— 也和 01 阶段在 vLLM 吞吐曲线上看到的宏观现象对上了：那边是现象，这里是机制。

意外两个没预料到的发现↑

一、K1 的 211.911 ms 里，四分之三和"不合并"无关↑

            N=4096（2 的幂）    N=4097（打破对齐）
K1           211.911 ms          63.675 ms     ← 快了 3.33 倍
K1/K2          8.209×             2.392×

8.209 ÷ 2.392 = 3.43   ← 2 的幂跨度的额外惩罚
回乘检验：2.392 × 3.43 = 8.209，逐位相同

N=4096 时 A 的行跨度恰好 16384 字节，warp 的 32 个地址全部撞进同一批 L2 set / DRAM bank。 所以"合并访存是性价比最高的一步"要加个注： 那 8.21 倍里只有 2.392 倍是合并本身，另外 3.43 倍是顺带治好的跨度冲突。 对照组：同一个 4096→4097，其余 kernel 只慢 2.8%–7.1%，cuBLAS 慢 15.7%。

预测结果意味着什么

K5 的 LDS.128 = 0推翻 K5→K6 不是"标量 vs 向量化"，是"部分 vs 完全向量化"。 真实指令比 2.32×，而非手推的 3.98×

二、那张"合并效率"图的三条腿替代论证↑

最后那个指标想证明的是"K1 的 8.21 倍劣势来自访存不合并"。没有它，这件事照样能证：

证据证明了什么
①K1 和 K2 的 SASS 逐项相同 8.21 倍里指令条数贡献严格为零，100% 是访存行为
②请求账 33 → 2 请求/FMA 机制：一条 LDG 被拆成 32 个请求 vs 合并成 1 个
③N=4097 把 8.209× 拆成 2.392× × 3.43×，回乘逐位对上 进一步分出"不合并"和"2 的幂跨度"各占多少
 ① 是排除法，比 ncu 的测量法更干净 —— 它不是量访存效率，是直接排除了另一个自变量。 ③ 更是 ncu 看不出来的： sector 指标只会告诉你效率低，不会告诉你其中四分之三是跨度冲突。

实测确认 nsys 在这种容器里能跑（CUDA 时间线可用）， 但它的 --gpu-metrics-devices 走同一条权限路径，同样报 ERR_NVGPUCTRPERM。
