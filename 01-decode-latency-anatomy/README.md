# 01 · 把一个 7B 拆开量：一张 4090 上的推理性能解剖

> 同一张 RTX 4090、同一个 Qwen2.5-7B，**吞吐 22 倍、首字延迟 215 倍的差距，全看你怎么发请求**
> （分别在并发扫描与过载实验中测到）。
>
> 这个仓库做了两件事：**先从模型结构把关键常数算出来，再用压测逐一验证。**
> 一份逐层结构拆解 + 10 组压测、7,594 条请求、两轮跨机器独立复现，原始数据一条没删。

---

## 30 秒结论

| 问题 | 答案 | 出处 |
|---|---|---|
| **这块内存为什么是 56 KiB/token？** | 从模型结构逐层推：`2×28层×4 KV头×128 dim×2B`。GQA 让它比 MHA **小 7 倍** —— 这个数决定了并发上限 | [结构拆解](Reports/Qwen2.5-7B%20结构拆解.html) |
| **选 vLLM 还是 llama.cpp？** | 分界线不是并发数，是**延迟预算**：p99 TTFT ≈ **730 ms**。比这紧 llama.cpp 赢，比这松 vLLM 赢 | [选型指南](Reports/Round2/06-选型指南-vllm-llama-cpp.html) |
| **这张卡能扛多少并发？** | **不用压测，可以算**：KV 每 token 占 56 KiB，池子 ÷ 上下文即上限。实测与理论差 **0.045%** | [KV 的线性](Reports/Round2/03-vllm-KV的线性.html) |
| **并发加到多少开始亏？** | 吞吐到 C=64 都没饱和，但 **C=8 起 ITL 尾部裂开**（p99 从 17.6 → 102.1 ms） | [并发曲线](Reports/Round2/01-vllm-Qwen2.5-7B并发曲线.html) |
| **首字延迟慢，该换卡吗？** | 过载时 **98.9% 的 TTFT 是排队**，真正算 prefill 只要 1.10 秒。换 H100 救不了，限流才行 | [TTFT 解剖](Reports/Round2/02-vllm-TTFT解剖.html) |
| **KV 池压爆会怎样？** | 超卖 **4.4 倍**、KV 顶到 100%、抢占 38 次 —— 结果**零失败、输出 token 一个不少** | [断崖](Reports/Round2/04-vllm-断崖.html) |
| **量化到底省下了什么？** | 省字节（单流快 **2.71×**），**省不了调度**（C=64 批处理效率 81% vs 25%） | [llama.cpp 压测](Reports/Round2/05-llama-cpp-压测.html) |

## 六个最硬的发现

### 1 · 容量可以纯算术推出来，压测只用来标定

每 token 的 KV 字节完全由模型结构决定，不需要试
（推导见[结构拆解](Reports/Qwen2.5-7B%20结构拆解.html)第 09 节）：

```
2 (K,V) × 28 层 × 4 KV head × 128 dim × 2 B = 57,344 B = 56.0 KiB
```

固定并发 16、输入从 256 扫到 4096，对 KV 占用做线性拟合：

| | 实测 | 理论 | 偏差 |
|---|---|---|---|
| 拟合斜率 | **15.9928** | 16.00（= 并发数） | **0.045%** |
| R² | **0.99993** | — | — |
| 池容量对账 | 6.41 GiB ÷ 56 KiB = 120,025 tok | 启动日志 120,064 | 0.03% |
| 8192 上下文的并发上限 | 14.65 条 | 启动日志 `14.66x` | 0.07% |

同一个 56 KiB **被两条完全独立的路径验证**：一条靠容量计数器，一条靠 ITL 斜率
（实测 0.00098 ms/token vs 纯带宽推算 0.00091，吻合 93%）。

### 2 · 抢占不是崩溃，是一个负反馈控制环

把 KV 池超卖 4.4 倍（需求 28 GiB / 池子 6.41 GiB）之后：

- 38 次抢占，**触发点稳定在 KV = 99.58%** —— 两台不同的机器测到**同一个数**
- 每次只踢一条，释放 **5.20 个百分点 = 6,242 token**，正好是一条请求的上下文
- 平均间隔 11.2 秒，几乎完全均匀 —— **过载下抢占是稳态的一部分，不是偶发事件**
- 128 条请求**全部成功返回**，每条精确 2,048 个输出 token

**PagedAttention 加抢占重算，把「资源不够」翻译成了「排队更久」，而不是「请求失败」。**
代价全部记在延迟上，一分没记在正确性上。

### 3 · p99 ITL 看不见抢占 —— 一条反直觉的监控经验

直觉是「被抢占的请求要重算，p99 ITL 会出现尖峰」。实测**不成立**：

```
128 条 × 2047 个间隔 = 262,016 个 ITL 样本
38 次抢占 ÷ 262,016 = 0.0145%   →  落在 p99.99 上，p99 根本够不着
```

抢占的监控指标只有两个：`num_preemptions_total` 和 **TTFT 尾部**。两轮独立复现。

### 4 · 真正的自变量既不是并发数，也不是序列长度

两组完全独立的实验 —— 一组固定长度扫并发（1→64），一组固定并发扫长度（256→4096）——
换算成**每步 token 数**（`tok/iter`）之后，**落在同一条曲线上**：

| 两条轴逐点相减 | MFU | MBU |
|---|---|---|
| 最大偏差 | **≤ 0.7 个百分点** | **≤ 3.6 个百分点** |

实用含义：想估一个没测过的配置落在哪堵墙上，不用管它是「高并发短上下文」还是「低并发长上下文」，
**先把 tok/iter 算出来**，再到这条曲线上查。

### 5 · 量化省的是字节，省不了调度

字节账能算到小数点后两位：

```
vLLM  bf16    权重 14.14 GB + KV 0.07 GB = 14.21 GB
llama Q4_K_M  权重  4.68 GB + KV 0.07 GB =  4.75 GB

预测步长比  14.21 ÷ 4.75 = 2.99×
实测        15.83 ÷ 5.84 = 2.71×   （达成预测的 91%）
```

差的那 9% 是解量化吃掉的带宽预算（MBU 89% vs 81%）。**但批处理红利完全是另一回事：**

| | vLLM | llama.cpp | 理论地板 |
|---|---|---|---|
| 每多一条并发的边际成本 | **0.106 ms/槽** | 0.468 ms/槽 | 0.066 ms/槽（两边相同） |
| 并发 1→64 的步长增幅 | **+42%**（地板 +29%） | +505%（地板 +88%） | — |
| C=64 roofline 达成率 | **81%** | 25% | — |

边际成本那一行是关键：多接一条并发，理论上只该多读那一条的 KV（0.066 ms）。
vLLM 付 0.106（地板的 1.6 倍），llama.cpp 付 0.468（**7.1 倍**）——
差的这 0.36 ms **和权重精度毫无关系**，它是 PagedAttention、continuous batching、
CUDA graph 复用这些调度侧工程的价值。

两条吞吐曲线在 **C ≈ 8.3** 换位。**Q4 的优势区间是低并发。**

### 6 · 两个计数器打架，说明指标本身要交叉验证

过载那一轮里，同一件事的两个计数器给出了相反的答案：

```
iteration_tokens_total  = 1,048,576 = 128 × 8192    ← 精确等于理论下限，一个 token 都没多记
estimated_flops_total   比模型标定值多出 +29%        ← 换算回约 30 万 token 的重算
独立校验：38 次抢占 × 6,242 token = 23.7 万 token    ← 与 FLOPs 账同量级
```

**抢占造成的重算真实发生了，但调度器的 token 计数器完全没记。**
在源码层面确认之前，涉及抢占的场景下 MFU / 算术强度都应以 FLOPs 计数器为准。

## 如果你要在生产上跑它

每一条都能从上面的数据直接推出来。

1. **先定 SLO，再反推并发，不要先定并发。**
   p99 TTFT 从 500 ms 放宽到 2000 ms，最优引擎会**换人**。
   把 `p99 TTFT < X` 写进配置文档，比写 `max-num-seqs = N` 有意义得多。

2. **容量红线抄启动日志那一行。**
   vLLM 的 `Maximum concurrency for N tokens per request: M` 是用 `KV池 ÷ max_model_len` 算的，
   两轮实测都只比它高 **5%–7%**。不需要压测就能做容量规划。

3. **缩短 `--max-model-len` 比加卡便宜。**
   容量红线与它成反比：8192 → 4096 直接把可驻留请求数翻倍。多数业务的真实上下文远小于配置值。

4. **把 `--max-num-seqs` 设成真实容量，而不是留着默认值。**
   实测设 128 时，调度器放进 18–19 条、再靠抢占踢回 15–16 条 —— 38 次抢占全是这么来的。
   按日志的 `14.66x` 设成 14，抢占理论上降到 0。**注意这个值跟着机器走。**

5. **监控只盯三个指标**：`ITL p50`（解码健不健康）、`waiting` 队列长度（容量够不够）、
   `num_preemptions_total`（有没有在做无用重算）。
   **TTFT 是结果不是原因，盯着它诊断不出问题。**

6. **过载时唯一有效的手段是限流，不是加速。**
   压爆那一轮用户等的 169 秒里，有 168 秒在等前面的人。
   在服务端设并发上限 + 前置队列长度上限、让超出的请求快速失败（429），
   比让它们排 169 秒有用得多 —— 后者还占着连接和客户端超时预算。

7. **ITL 和 TTFT 谁在爆，直接指向两种不同的病。**

   | 症状 | 诊断 | 处方 |
   |---|---|---|
   | ITL 正常 + TTFT 爆炸 | 容量不够，在排队 | 加卡、减并发、缩 `max_model_len`、上限流 |
   | ITL 也慢 | 解码本身有问题 | 查 batch 配置、kernel、量化实现 |

## 为什么这些数可信

- **跨机器两轮独立复现。** 相隔十天、换了实例、换了驱动版本，七个并发点的吞吐差异全部落在
  **−1.20% ~ +0.61%**；ITL 裂口位置、混批比例、KV 对账误差、抢占触发线 99.58% —— 全部复现。
- **每轮跑完立刻做自检**：输出 token 数是否精确等于设定值、`--temperature 0` 是否真的生效、
  prefix caching 是否真的关着、失败请求数、抢占计数。**自检不过的数据不进报告。**
- **一个被证伪的假设也写了进去。** 第二轮的动机是「第一轮的 `repetition_penalty` 让 vLLM 偏悲观」——
  结果七个档位的差异全在 ±1.2% 噪声内，**假设是错的**。
  但它把「采样参数不同构」从怀疑名单里划掉了。**排除一个假设也是结果。**
- **跨引擎对比时发现了一个坑**：`--ignore-eos` 在两个引擎上行为不一致 ——
  vLLM 每条精确 256 个输出 token，llama.cpp 是 250–256 不等，合计差 **1.35%**。
  已在报告中披露，并说明它对结论无影响。
- **原始数据一条没删**，都在 [`Results/`](Results/) 下：bench 原始 JSON、1 Hz 采样 CSV、
  服务端完整日志、环境指纹。报告里每个数都能追回源文件。

## 诚实：没搞清的、没测的

**没搞清的**

- llama.cpp 在 **C=32 那一档的异常塌陷**（444 tok/s，比它自己的 C=16 还低）。
  该档的 CUDA graph 复用率**从 99.22% 归零**，相关性极强，但因果需要
  `-DGGML_CUDA_USE_GRAPHS=OFF` 的对照实验才能闭合。**在那之前这一档不写进任何结论。**
- `iteration_tokens_total` 与 FLOPs 计数器在抢占场景下的矛盾，需要在源码层面确认记录点。

**没测的**

- **KV 量化**（`-ctk q8_0`）—— 权重量化的红利随 batch 变小，**KV 量化的红利随 batch 变大**，
  这是比权重量化更有意思的旋钮。
- 池子大小的受控实验。两轮之间 KV 池差 38% 是驱动与显存 profiling 的**意外**，不是设计。
- llama.cpp 的 `-c` 没有调平，本轮把量化省下的显存又按满配吃了回去。
- 多卡、投机解码、chunked prefill 调参、其他模型规模。

## 怎么复现

完整命令串（开机 → 装环境 → 起服务 → 4 项验证 → 压测 + 采样 → 切引擎对比 → 收工）
见 [`Scripts/第二轮测试脚本.md`](Scripts/第二轮测试脚本.md)。三条关键规矩：

1. **一份 `sweep.sh` 打两个端口。** 跨引擎对比的客户端必须完全一致，
   并显式写死 `--temperature 0`、`--random-range-ratio 0`、每档独立 seed。
   *服务端的默认值是变量，不是常数。*
2. **压测期间不许改服务端配置。** 起服务到收工前，`vllm serve` 的参数一个字不动。
3. **每轮跑完立刻抄两行启动日志**：`GPU KV cache size` 与 `Maximum concurrency`。
   凡是从 KV 池推出来的数（并发上限、抢占阈值）**必须每台机器现读**，不能跨机器搬。
