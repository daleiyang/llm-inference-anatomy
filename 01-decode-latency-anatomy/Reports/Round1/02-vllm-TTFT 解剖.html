结论TTFT 的增长几乎全部来自排队

把 TTFT 拆成"排队"和"真算"两段之后,结论很干脆:从 C=1 到 C=64, prefill 只涨了 5 倍,而排队从 0 涨到 379 毫秒。 并发越高,用户等的越不是计算,而是别人。

核心分解结果 · C=64

排队 379 ms  +  prefill 461 ms  +  前端 136 ms

三段加起来 976 ms,正是客户端观测到的平均 TTFT。 其中排队从 C=1 的 0 ms 一路涨到 379 ms,是唯一一个近乎从零起步的分量。

分解TTFT 拆成三段

服务端的 request_queue_time 和 request_prefill_time 两个 histogram, 差分后得到每个并发点的平均排队时间与平均 prefill 时间。 两者之和与客户端观测的 TTFT 之间还差一截,那是 vLLM 前端(API server)的处理与 IPC 开销。

两个分量的增长速度完全不同

这解释了第一轮的一个悬念

第一轮看到 C=64 的 p99 TTFT 高达 5.77 秒而 p50 只有 782 ms,当时只能推测"少数请求被排到了后面"。 现在有了直接证据:C=64 时有 13% 的采样点观测到排队,waiting 队列峰值达 49 条。 而 running 的中位数是 62,低于设定的 64 —— KV 池确实开始限制并发了。

混批每次迭代里,八成 token 属于别人的 prefill

iteration_tokens_total 记录每次 engine 迭代处理了多少 token。 如果只有 decode,这个数应该等于 batch size。实测是 batch 的 5 倍 —— 多出来的部分就是被 chunked prefill 塞进来的 prefill 块。

这是 ITL p99 尖峰最直接的物理解释:一个正在解码的请求,每一步都要等同批次里的 prefill 块算完。C=64 时每次迭代要处理 321 个 token,其中约 259 个是 prefill, 于是解码方向的每一步都被拖长,尾部就出现了 200 ms 量级的停顿。

波形917 秒全程实况

这是第一轮完全没有的视角。七个并发点在时间轴上依次排开, 可以直接看到队列什么时候堆起来、KV 什么时候冲顶。

功耗墙可能是效率衰减的一部分原因

C=64 时 GPU 持续运行在 440 W,而 C=1 只有 314 W。撞上功耗限制后 GPU 会降频, 这会直接压低实际可用带宽和算力 —— 而 vLLM 的任何指标都看不到这件事。 第一轮把 C=64 效率只有 35.7% 全部归因于 prefill 抢算力,现在看至少还要算上功耗墙这一份。

对账PagedAttention 的账,算得平不平

这是原计划里的实验 3-A。KV 占用不该是个测出来才知道的黑箱 —— 它应该能从并发数、序列长度、每 token 的 KV 体积三个数直接算出来。 拿稳态实测值去对,误差有多大就说明这本账理解得有多准。

先把口径分清楚

原公式写的是 并发 × (in_len + out_len) × 56 KiB ÷ 池大小。 但 in + out = 1280 是请求结束那一刻的占用, 稳态下大量请求正生成到一半,平均只占 in + out/2 = 1152。 峰值要对峰值,均值要对均值,混用会系统性高估 11%。

账算平了

峰值口径误差 0.0 ~ −1.0 个百分点,七个点全部落在 1 pp 以内。 均值口径在低并发下同样贴合,只有 C=64 出现 −2.7 pp 的偏差。

而这个偏差不是模型错了,是"名义并发 ≠ 实际并发"。 C=64 时 KV 池已经限制了调度,running 中位数只有 62。 用 62 代入公式:预期 82.2%,实测 82.1% —— 误差 0.1 个百分点。

剩下 C=8~32 那 −0.3 ~ −1.6 pp 的小幅负偏差,来自请求生命周期错开: 理论均值假设输出进度均匀分布在 0~256 之间,但请求完成到新请求 prefill 完成之间 有短暂空隙,实际占用略低于理想值。这个方向和量级都合理。

一个这轮没暴露的坑

本例的 1280 和 1152 都能被 block_size=16 整除,所以对齐损耗恰好为零。 换成 in_len=1000 就不一样了:ceil(1256/16)=79 blocks = 1264 tokens, 每请求白占 8 个 token。并发 64 时就是 512 个 token 的浪费 —— 量不大,但做容量规划时要记得按 block 向上取整,而不是按 token 数直接算。

对照第一轮的结论,哪些站住了

被证实的

  • ITL 尾部在 C=8 裂开 —— 两轮完全一致(p99 从 17.4 跳到 99.2 ms), 而且现在有了机制层面的证据:每次迭代混入了 4 倍于 decode 的 prefill token。
  • 抢占不是原因 —— 采样器全程 913 个点,num_preemptions_total 始终为 0,比第一轮只查日志更有说服力。
  • KV 池是真实天花板 —— C=64 时 KV 占用峰值 93.3%, 与按 86,896 tokens 算出的 94.3% 吻合;running 中位数 62 < 64 也印证了这一点。
  • PagedAttention 的账完全算得平 —— 七个并发点的峰值占用 与理论预期误差全部在 1 个百分点以内。这意味着 KV 容量可以事先算准, 不需要试出来。

被修正的

  • "TTFT 增长主要来自 prefill"这个说法不准确。 实际上 prefill 只涨了 5.0 倍,排队从第一个可测点(C=4 的 1.0 ms) 涨到 379 ms —— 379 倍。 但要说清楚:排队在本轮全程都没有超过 prefill, C=64 时也只追到 82%;按斜率外推,超越要到 C≈73 才发生。
  • 效率衰减不只是 prefill 抢算力。C=64 时 GPU 持续 440 W 贴着功耗墙, 降频的影响没有被计入第一轮的分解。

新发现

  • vLLM 前端有不可忽略的开销,从 C=1 的 12 ms 增长到 C=64 的 136 ms, 占 TTFT 的 14%。这部分在 EngineCore 的任何指标里都看不到, 只能靠"客户端 TTFT 减服务端分段"倒推。
  • 混批比例恒定在 1:4,不随并发变化 —— 它由输入输出比(1024:256)决定, 而不是由调度策略决定。
  • KV 对账要区分峰值与均值两个口径。 in + out 是请求结束那一刻的占用,稳态均值应该用 in + out/2, 两者差 11%。混用会以为模型算错了,实际上只是口径不对。

一个没做成的验证

本轮原计划用 estimated_flops_per_gpu_total ÷ estimated_read_bytes_per_gpu_total 实测算术强度,验证理论推导的 1.0 FLOP/byte。 但这两个 counter 全程为 0 —— 它们需要启动时加 --enable-mfu-metrics 才会计数。下一轮补上即可。

下一步三件值得做的事

  • 开 --enable-mfu-metrics 重跑 C=1, 拿 ΔFLOP ÷ Δbytes 验证算术强度 = 1.0。这是理论推导唯一还缺的实测对照。
  • 加 --kv-cache-memory=6569114112 扩池到 6.12 GiB, 并发上限从 67 提到 89,然后补测 C=96。现在已知 C=64 时 waiting 峰值 49、 running 卡在 62,扩池后应该能看到明显变化。
  • 调低 --max-num-batched-tokens 再跑一轮, 验证"prefill 块变小 → ITL 尖峰变矮、TTFT 变差"这个对换关系。 现在有了 iteration_tokens 指标,可以直接量化块大小的变化。
