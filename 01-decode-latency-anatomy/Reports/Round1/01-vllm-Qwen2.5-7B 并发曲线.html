结论拐点在 C=8 到 C=16 之间

吞吐一路涨到 C=64 都没有真正饱和,但"每多给一个并发槽换来多少 token/s"从 C=8 起就掉得很快。 真正划线的不是吞吐曲线,是 ITL 的尾部 —— 它在 C=8 那一点突然裂开。

曲线吞吐与延迟的兑换率

横轴是实际产出的 token/s,纵轴是 p99 首字延迟(对数)。曲线越往右越贵 —— 从 C=1 走到 C=16 花了 1.28 秒 p99 TTFT 买到 11 倍吞吐;从 C=32 走到 C=64 只多买到 36% 吞吐,却付出了 2.9 秒。

效率并发翻倍,吞吐没有翻倍

双对数坐标下,理想线性扩展是一条直线。实测曲线从 C=4 开始明显偏离, 到 C=64 时只剩理想值的 35.7%。

每多一个并发槽,还能换来多少

这是判断拐点最直接的量。第一个并发槽带来 56.6 tok/s,到 C=32→64 那一段, 每个槽只剩 11.6 tok/s —— 边际收益衰减到五分之一。

断点ITL 的尾部在 C=8 裂开

这是整轮压测里最值得看的一张图,也是"P99 ITL 才暴露抖动"这句话最干净的实证。 p50 ITL 从 C=1 到 C=64 只从 15.9 ms 涨到 22.7 ms —— 涨了 43%,温和得看不出问题。 但 p99 ITL 在 C=8 那一点从 17.4 ms 直接跳到 99.6 ms,一步跳了 5.7 倍。

这不是抢占

服务端日志里 preempt 出现 0 次,Waiting 队列最长只有 3 条。 所以尾部延迟不是 KV 不够导致的请求被踢出重算。

真正的原因是 enable_chunked_prefill=True(日志确认): 新请求的 prefill 被切块后混进正在解码的批次。 对已经在解码的请求来说,那一步要等 prefill 块算完,于是出现一个 100–200 ms 的停顿。 C=64 时 p90 ITL 已达 188 ms —— 超过一成的 token 间隔卡在别人的 prefill 上。

这些停顿最终反映在端到端时间上

天花板真正的上限是 67,不是 128

服务端启动参数写的是 --max-num-seqs 128,但那只是名义上限。 实际能同时跑多少条,由 KV cache 池除以单请求占用决定。 

# 服务端日志实测
Available KV cache memory: 4.64 GiB
GPU KV cache size:         86,896 tokens

# 单请求占用 = 输入 + 输出
1024 + 256 = 1,280 tokens

# 真实并发上限
86,896 ÷ 1,280 = 67.9 条

有 1.48 GiB 显存没被用上

显存账:权重 + non-torch 15.49 GiB,峰值激活 1.04 GiB,CUDA Graph 0.34 GiB, KV 池 4.64 GiB,合计 21.51 GiB。而 --gpu-memory-utilization 0.90 给出的预算是 21.17 GiB,卡上总共有 23.52 GiB。

vLLM 自己在日志里给了建议:--kv-cache-memory=6569114112(6.12 GiB)。 照做能把池子扩到约 114,600 tokens,并发上限从 67 提到 89, 而且不需要动 gpu-memory-utilization。

下一步该改什么

  • 先把 KV 池调满。加 --kv-cache-memory=6569114112, 池子 4.64 → 6.12 GiB,并发上限 67 → 89。这是唯一一个纯赚不赔的改动。
  • 再补测 C=96。扩池之后 C=96 才有意义,可以看到吞吐是否还能越过 1,405 tok/s, 以及 KV 逼近 100% 时是否终于出现 preemption。
  • ITL 抖动想压下去,调 --max-num-batched-tokens。 调小 → prefill 块更细 → ITL 尖峰更矮,但 TTFT 会变差。这是一个明确的对换, 取决于你的场景是流式聊天(在意 ITL)还是批量任务(在意 TTFT)。
  • 补上脚本里漏掉的 --random-range-ratio 0。 本轮 total_input_tokens 正好是 1024 × num_prompts,说明这个版本默认是定长, 结果可信;但换台机器或换个版本就不一定了。
  • C=1~C=8 的 p99 不要引用。样本量分别是 40/60/80/120, 算 p99 等于取最慢的那一两条,是噪声不是信号。
