参数个数        512 × 3584 = 1,835,008     ← 两种写法数量相同

03.2三维张量怎么和二维权重相乘↑ 目录

[B, S, 3584] 是三维的,权重是二维的。实际执行时 batch 和序列两维会被压平: 

[B, S, 3584]  --reshape-->  [B·S, 3584]     ← 把每个 token 当成独立的一行
                                  │
                            一次 GEMM:  [B·S, 3584] @ [3584, 3584]
                                  │
              [B·S, 3584]  --reshape-->  [B, S, 3584]

# 关键推论:token 之间在投影这一步【互不影响】。
# 唯一让 token 互相"看见"的地方,是注意力核里的那两次矩阵乘。

这也解释了 batch 为什么"几乎免费":B·S 只是把 GEMM 的一边变长, 权重那一边一个字节都没多读。这就是 continuous batching 的物理基础。

03.4「FLOPs = 2 × 参数量」是怎么来的↑ 目录

这条经验公式在算 MFU 时会反复用到,但它不是天上掉下来的。从矩阵乘的定义式推一遍: 

# 矩阵乘的定义:C = A @ B,其中 A 是 [m,k],B 是 [k,n],C 是 [m,n]

C[i,j] = A[i,0]·B[0,j] + A[i,1]·B[1,j] + … + A[i,k−1]·B[k−1,j]
         └──────────────────── k 项相加 ────────────────────┘

# 也就是说:【每一个输出元素,都是一个长度为 k 的点积】

所以"每个输出元素乘一次加一次"这句话,准确的说法是 「点积里每前进一项,就是一次乘 + 一次累加」: 

算 C[i,j] 要做:
    k 次乘法        A[i,p] · B[p,j]        p = 0 … k−1
  k−1 次加法        把 k 个乘积加起来
  ─────────────────────────────────────
  = 2k − 1 次浮点运算

# 惯例上写成 2k —— 因为实现时累加器从 0 开始,第一项也做一次加法,
# 而且 k 一大,那个 −1 就无关紧要了(k=3584 时误差 0.014%)。

03.6为什么一个 token 就是「2 × 权重数」↑ 目录

一个 token 的隐藏向量是【一行】:  x 形状 [1, 3584]     ← m = 1
q_proj 的权重:                    W 形状 [3584, 3584]   ← k=3584, n=3584

FLOPs = 2 · m · k · n
      = 2 · 1 · 3584 · 3584
      = 2 · (3584 × 3584)
      = 2 · 权重矩阵里的元素个数
      = 2 × 12,845,056 = 25.69 MFLOP

# m=1 把 m 从式子里消掉了,于是 k·n 恰好就是权重的参数量。
# 这就是「FLOPs = 2 × 参数量」的全部来历 —— 它只对【每个 token】成立,
# batch 或 prefill 有 S 个 token 时,要再乘 S。

FMA:硬件一条指令,但仍然记 2 FLOPs

GPU 上 a·b + c 是一条融合乘加指令(FMA), 一个时钟周期就能出结果。既然只发了一条指令,为什么还算 2 次运算?

因为 FLOPs 数的是算术运算的个数,不是指令条数。 更关键的是:NVIDIA 标称的峰值算力本身也是按 FMA=2 算的 —— 4090 的 165 TFLOPS 就等于 2 × CUDA核心数 × 时钟 × …。 分子分母用同一套口径,MFU 才有意义。两边都改成 1,比值不变;只改一边就错了一倍。

04注意力分支:四个矩阵,两种尺寸↑ 目录

关键的不对称在这里 —— q_proj 和 o_proj 是 3584 → 3584 的方阵, 而 k_proj / v_proj 只输出 512。 因为 K/V 只有 4 个头:4 × 128 = 512。这一步是 GQA 的全部秘密。

05注意力核内部:五步,两次矩阵乘↑ 目录

上一节说"Attention 本身一个参数都没有"。那它在算什么? 五步:切头 → 打分 → 掩码 → 归一 → 加权求和。 只有第 2 步和第 5 步是矩阵乘,其余都是逐元素或按行操作。

05.1切头:一次 reshape,不是 28 次矩阵乘↑ 目录

q_proj 出来        [B, S, 3584]
                        │  view(B, S, 28, 128)      ← 3584 = 28 × 128
                   [B, S, 28, 128]
                        │  transpose(1, 2)
                   [B, 28, S, 128]                  ← 头维提到前面当 batch
                        │
              28 个 [S,128] 的矩阵并行做上面五步

# "多头"不是 28 组不同的权重,而是【一个大矩阵的输出被切成 28 段】。
# q_proj 的 3584 个输出通道,前 128 个属于头 0,接下来 128 个属于头 1……

05.2GQA 的广播:K/V 只有 4 组,怎么配 28 个 Q 头↑ 目录

Q   [B, 28, S, 128]        28 个头,各不相同
K   [B,  4, S, 128]        只有 4 组
V   [B,  4, S, 128]

                 ↓  repeat_interleave(7, dim=1)   ← 每组复制 7 份

K'  [B, 28, S, 128]        头 0-6 用同一份 K,头 7-13 用下一份……
V'  [B, 28, S, 128]

# 关键:复制发生在【寄存器/共享内存里】,不是在 KV Cache 里。
# 缓存的永远是那 4 组,所以显存省 7 倍;
# 参与矩阵乘的是 28 组,所以 FLOPs 一分不省。

实现上更进一步:FlashAttention 这类 kernel 根本不做物理 repeat, 而是让 7 个 Q 头直接索引同一块 K/V。 于是这 7 个头读的是同一段显存 —— 在 decode 这种访存瓶颈下, 这一份数据被 L2 缓存住,7 个头只付一次带宽。 这是 GQA 除了省显存之外的第二重收益。

05.3RoPE:位置信息是"转"进去的,不是"加"进去的↑ 目录

RoPE 没有参数,它把 Q 和 K 的 128 维两两配对成 64 个复数, 第 i 对按角度 θᵢ · pos 旋转: 

对第 i 对分量 (x₂ᵢ, x₂ᵢ₊₁),位置 pos:

  x'₂ᵢ   = x₂ᵢ·cos(θᵢ·pos) − x₂ᵢ₊₁·sin(θᵢ·pos)
  x'₂ᵢ₊₁ = x₂ᵢ·sin(θᵢ·pos) + x₂ᵢ₊₁·cos(θᵢ·pos)

  θᵢ = base^(−2i/128)        Qwen2.5-7B 的 base = 1,000,000

# 为什么这样设计:两个向量旋转后做点积,结果只依赖【相对位置差】,
# 与绝对位置无关 —— 这就是"相对位置编码"的由来。

RoPE 只作用于 Q 和 K,不碰 V

因为位置信息是用来决定"谁该关注谁"(打分,即 QKᵀ), 而不是用来改变"关注到什么内容"(取值,即 V)。 工程上的后果:KV Cache 里存的 K 是已经旋转过的, 所以缓存不能跨位置复用 —— 同一段文本出现在不同位置,K 的值不一样。

05.4常数 200,704 是怎么算出来的↑ 目录

注意力核那五步里,只有第 ① 步和第 ⑤ 步是矩阵乘,其余(缩放、掩码、softmax)都是逐元素或按行。 所以只需要数这两步。单个头、单层、序列长度 S: 

# ① scores = Q @ Kᵀ
  [S, hd] @ [hd, S] → [S, S]
  按 2·m·k·n:  2 · S · hd · S  =  2·hd·S²

# ⑤ out = P @ V
  [S, S] @ [S, hd] → [S, hd]
  按 2·m·k·n:  2 · S · S · hd  =  2·hd·S²

# 两步相加
  单头单层(完整)  =  4·hd·S²  =  4 × 128 × S²  =  512·S²

然后三步放大 / 缩小:

① × h = 28 个 Query 头          512·S² × 28   =  14,336·S²

② 因果掩码,只算下三角  ÷ 2      14,336·S² ÷ 2 =   7,168·S²
   上三角的 scores 反正会被 −∞ 掩掉,kernel 直接跳过不算;
   PV 那一步 P 是下三角矩阵,第 i 行只需要累加 j ≤ i 的项,同样省一半。

③ × L = 28 层                  7,168·S² × 28 =  200,704·S²
                                                 ↑ 这就是那个常数

⚠️ 这里用的是 h = 28,不是 kv = 4

GQA 把 K/V 压到 4 组,但计算时它们会广播成 28 份(见上文), 28 个 Query 头每一个都要完整地算一遍 QKᵀ 和 PV。 所以注意力核的 FLOPs 用的是 Query 头数。 如果错用 kv=4,这个常数会变成 28,672,小了 7 倍。

这正是本文反复强调的那句话的量化版本:GQA 省的是显存,不是算力。

05.5decode 的常数是 401,408,正好是 2 倍↑ 目录

# decode:只有 1 个 query,但要看 T 个历史位置

  ① q[1, hd] @ Kᵀ[hd, T]  → [1, T]     2 · 1 · hd · T  = 2·hd·T
  ⑤ p[1, T]  @ V[T, hd]   → [1, hd]    2 · 1 · T · hd  = 2·hd·T

# 因为 decode 【没有因果折半】—— 那唯一的 query 要看【全部】T 个历史位置,
# 一个都不能跳。少了 ÷2,常数就翻倍。

一致性检查:两条路算出来是同一个数

如果逐 token 生成一段长度 S 的序列,总注意力开销应该等于一次性 prefill 这 S 个 token: 

逐 token 累加   Σ 401,408 · t   (t = 0 … S−1)
              = 401,408 · S(S−1)/2
              ≈ 200,704 · S²          ← 和 prefill 公式一模一样

S = 8,192 实算:  1.3467e13  vs  1.3469e13   比值 0.9999

两条完全独立的推导路径收敛到同一个式子,说明常数没算错。

式子里那个 T 就是 KV Cache 里已经堆了多少行 —— 它每生成一个 token 就 +1。这些行是怎么攒起来的、为什么永远不用重算, 见下文 KV Cache:决定并发上限的那块内存 一节。

但真正的墙不是 FLOPs,是显存 —— 这才是 FlashAttention 存在的理由

看表格最后一列。S×S 的分数矩阵,单个头在 S=8192 时就是 128 MiB; 28 个头同时物化,一层就要 3.5 GiB。 到 S=32768,单头 2 GiB、28 头 56 GiB —— 任何一张卡都放不下。

被忽略的零头:softmax 和缩放

这两项都作用在那个 S×S 的分数矩阵上,所以也是 S² 量级。 但常数小得多,数一遍就清楚: 

# softmax:对每一行做数值稳定版归一,逐元素数是 5 次
  ① 找本行最大值        max          1 次/元素
  ② 减去最大值          x − max      1 次/元素   防 exp 溢出
  ③ 取指数              exp(·)       1 次/元素
  ④ 累加求和            Σ            1 次/元素
  ⑤ 除以和              ÷ Σ          1 次/元素
                                    ──────────
                                     5 次/元素

  因果只有下三角 → 元素数 = S²/2
  5 × (S²/2) × h=28 × L=28  =  5 × 784 ÷ 2 · S²  =  1,960 · S²

# 缩放 ÷√128:每个元素就 1 次乘法
  1 × (S²/2) × 28 × 28      =      784 ÷ 2 · S²  =    392 · S²

# 和注意力核的两次矩阵乘比
  softmax   1,960 ÷ 200,704 = 0.98%
  缩放        392 ÷ 200,704 = 0.20%       两者都可以忽略

两个提醒。一是 exp 并不真的只值 1 次运算 —— 它在 GPU 上走特殊函数单元(SFU),吞吐比 FMA 低好几倍。 所以"5 次"是偏乐观的粗算;即便按实际代价乘 4~5 倍,也仍然只有几个百分点, 不改变"可以忽略"这个判断。

二是那个缩放实际实现里几乎不花钱:把 1/√128 提前乘进 Q(只有 S×128 个元素), 而不是乘进 scores(S²/2 个元素), 开销就从 392·S² 降到 100,352·S —— 从平方降到线性。S=8192 时省 32 倍,S=32768 时省 128 倍。

但注意:softmax 是 FlashAttention 唯一真正棘手的地方 —— 它需要全行的最大值和总和才能归一,而分块计算时拿不到全行。 解法是 online softmax:每处理一块就更新一次running max 和 running sum, 并把之前的部分结果按比例修正。这 1% 的运算量,决定了整个算法能不能成立。

06GQA:28 个 Query 头,只配 4 组 K/V↑ 目录

Multi-Head Attention 里每个 Q 头配一个自己的 K/V 头。GQA 让 7 个 Q 头共用同一组 K/V。 计算量几乎不变(K/V 广播复制到 28 份参与运算),但需要缓存的 K/V 少了 7 倍。

07MLP 分支:参数的大头在这里↑ 目录

SwiGLU 用了三个矩阵而不是传统 FFN 的两个。中间维度 18944 是 hidden 的 5.29 倍,三个矩阵每个都是 6790 万参数—— 一层的 MLP 就抵得上 7 层的注意力。

07.1门控到底在"门"什么↑ 目录

传统 FFN 是 out = W₂ · σ(W₁·x) —— 一个线性层、一个激活函数、再一个线性层。 SwiGLU 把中间那步拆成两条并行的投影,一条当"内容",一条当"闸门",逐元素相乘: 

gate = x @ W_gate        [B,S,3584] @ [3584,18944] → [B,S,18944]
up   = x @ W_up          [B,S,3584] @ [3584,18944] → [B,S,18944]

h    = SiLU(gate) ⊙ up   ← ⊙ 是逐元素乘,不是矩阵乘
out  = h @ W_down        [B,S,18944] @ [18944,3584] → [B,S,3584]

SiLU(z) = z · sigmoid(z) = z / (1 + e^−z)

07.2为什么值得多花一个矩阵↑ 目录

  • 乘法交互是线性层做不出来的。 σ(W₁x) 之后再线性变换, 整体仍然是"逐通道非线性 + 线性混合";而 SiLU(W_g x) ⊙ (W_u x) 含有 两个输入特征的乘积项。要用传统 FFN 近似一个乘法,需要相当多的神经元。
  • 开关是学出来的,而且是逐 token 的。 ReLU 的"关"取决于该通道自己的值; SwiGLU 的"关"由一路独立的投影决定 —— 网络可以学出 "当输入含有特征 A 时,把通道 k 关掉"这种条件逻辑。
  • 软门比硬门好训练。 ReLU 在负半轴梯度恒为 0(死神经元); SiLU 处处可导且负半轴梯度非零,配合门控结构收敛更稳。

代价:参数从 2·d·f 变成 3·d·f

业界惯例是把 f 缩到 8d/3 来抵消这多出来的 50% (d=3584 时是 9557,恰好等参数于 f=4d 的传统 FFN)。 但 Qwen2.5-7B 没有这么做 —— 它取 f = 18944 = 5.29 d, MLP 参数 203.7 M/层,是"等参数惯例"的 1.98 倍。

这是一个明确的架构取舍:把预算压在 MLP 而不是注意力上。 后果直接体现在工程上 —— MLP 占全模型 74.9% 的参数, 量化和稀疏化的收益几乎全在这里;而下一节的 MoE,动的正是这一块。

09KV Cache:决定并发上限的那块内存↑ 目录

量一下就知道谁才是并发的瓶颈

全部 28 层的 W_k 加 W_v 一共 102,760,448 个参数 —— 196 MiB,而且不管跑多少并发都是这么多。

而一条 1024+256 的请求,cache 峰值是 70 MiB。 也就是说 只要并发到 3,cache 就超过了生成它的那套投影矩阵本身; 并发 64 时 cache 是 4.38 GiB,是 W_k/W_v 的 23 倍。

这就是为什么并发上限由 KV 池决定,而不是由权重决定 —— 权重是一次性付清的固定成本,cache 才是随生意规模线性增长的可变成本。

prefill 和 decode 用的是同一套 W,只是批量不同

cache 里那些行不是凭空来的,prefill 阶段就是用同一个 W_k 一次性把整个 prompt 算完写进去的: 

prefill  H [1024,3584] @ W_k → [1024,512]   一次写入 1024 行
decode   h [   1,3584] @ W_k → [   1,512]   每步追加    1 行
         ↑ 同一个 W_k,同一块 cache,只是一次喂几行不同

所以整条时间线是:prefill 把 prompt 的 K/V 批量灌进 cache → decode 每步补一行 → 每步都拿新 q 去问整个 cache。 到这里,cache 里的内容从哪来、怎么长、谁在读,就闭合了。

存进去的 K 是 RoPE 之后的

位置编码在投影之后、写入 cache 之前就转好了(见上文 RoPE:位置信息是"转"进去的)。所以 cache 和绝对位置绑死 —— 同一段文本出现在不同位置,K 的数值不一样,缓存不能平移复用。 这也是 prefix caching 只能复用前缀、不能复用中间片段的原因。

核心:为什么 K/V 一经算出就永不改变

这是整个 KV Cache 能成立的唯一前提,而它的来源只有一个 —— 因果掩码。 

因果掩码 ⇒ 位置 i 的隐藏状态 h_i 只依赖位置 ≤ i 的输入
         ⇒ 在末尾追加 token t+1,【不会改变】任何 h_i (i ≤ t)
         ⇒ K_i = W_k · h_i  和  V_i = W_v · h_i  恒定
         ⇒ 算过一次,就可以永久复用

反例能说明这有多关键:BERT 那种双向注意力,每个位置都能看到全序列, 加一个 token 会改写所有位置的表示 —— KV Cache 在那里根本不成立。 所以"缓存能存在"不是工程技巧,是因果掩码这个建模选择白送的。

  平均 1,280 token / 请求  →  约 67 并发   (1024 输入 + 256 输出)
  平均 2,048 token / 请求  →  约 42 并发
  平均 4,096 token / 请求  →  约 21 并发

这个数每台机器都不一样,必须从日志读

配套压测的第二轮换了一台实例(驱动 580.159.03 / CUDA 13.0,第一轮是 590.48.01 / CUDA 13.1), 同样的启动参数量到的是 6.41 GiB / 120,064 token / 14.66x —— 比第一轮大 38%。差异来自权重占用和激活峰值的 profiling 结果随驱动版本波动。

所以手算只用来估数量级,真实值一律以启动日志的 GPU KV cache size 那一行为准。

这就是 preemption 的来源

并发压上去、上下文变长,一旦这 86,896 个槽位不够分,vLLM 就会把某些请求的 KV 换出去(swap)或直接丢弃重算(recompute)。 被换出的请求恢复时会产生一次几百毫秒的空档——正是 P99 ITL 上那根长尾。 日志里 Preemption 计数不为零,就说明你已经压到这条线了。

10MoE:把这一块 MLP 换成 64 块,每次只用 8 块↑ 目录

上一节算过:MLP 占了全模型 74.9% 的参数。 MoE(Mixture of Experts)动的正是这一块 —— 注意力分支、残差流、RMSNorm、KV Cache 全部原样不动, 只把每层那个 203.7 M 的 SwiGLU 换成"一堆小 SwiGLU + 一个路由器"。

为什么用 Qwen2-57B-A14B 当例子

因为它和 Qwen2.5-7B 的注意力几何完全相同: hidden 3584 · 28 层 · 28 Q 头 · 4 KV 头 · head_dim 128 —— 一个数都没变, 连 intermediate_size 18944 都一样。 唯一的差别就是 MLP 被换成了 MoE 块, 是一次干净的单变量对照。

直接后果:两个模型的 KV Cache 单价完全一样,都是 56 KiB/token。 MoE 不会让 KV 变大也不会变小 —— 它和上一节的容量公式毫无关系。

10.1共享专家那个 20480 是从哪里来的↑ 目录

先说结论:它不是从 18944 或 2560 推算出来的,而是 config.json 里一个独立的字段 —— Qwen2-57B-A14B 的 MoE 层一共写了三个不同的中间维,很容易看混:

一个 MoE 层里共存的三个中间维
config.json 字段值用在哪里
intermediate_size18,944 继承自稠密架构的字段。MoE 层里实际用不上,只是没删掉
moe_intermediate_size2,560 单个路由专家的宽度 × 64 个
shared_expert_intermediate_size20,480 就是图 12 里那个 20480 —— 共享专家一个人的宽度

但这三个数字并不是随便定的。20480 和 2560 之间有一个很干净的关系: 

  moe_intermediate_size  ×  num_experts_per_tok
        2560             ×          8            =  20480
                                                     ↑ 正好是 shared_expert_intermediate_size

# 换句话说:共享专家一个人,就有那 8 个被选中的路由专家加起来那么宽。

所以一个 token 走完一层 MoE,实际过的 FFN 宽度是 路由部分 20480 + 共享部分 20480 = 40960,恰好对半分。 图 12 底部那行"8 专家 220.2 M + 共享 220.2 M"两个数字一模一样,就是这个原因 —— 不是巧合,是 2560 × 8 = 20480 直接导致的。 

# 共享专家内部就是一个普通的 SwiGLU,只是宽度用 20480
  gate = x @ Wg[3584, 20480]        →  73,400,320
  up   = x @ Wu[3584, 20480]        →  73,400,320
  out  = h @ Wd[20480, 3584]        →  73,400,320
                                       ──────────
                        3 × 3584 × 20480 = 220,200,960
  gate = sigmoid(x @ W_sg[3584, 1]) →       3,584   共享专家自己的开关
                                       ──────────
                                       220,204,544   ← 表里"共享专家/层"那一行

# 对照被激活的 8 个路由专家(它们没有各自的开关,权重由 router 给)
                      8 × 3 × 3584 × 2560 = 220,200,960

# 再加上 router 本身(3584 × 64,不管选谁都要跑一遍)
                               3584 × 64 =         229,376
                                       ──────────
                    每 token 的 FFN 激活 = 440,634,880   ← 表里"FFN 激活/层"那一行

上面那个"共享专家自己的开关"是什么↑ 目录

它是一个独立的、只有一列的小线性层 W_sg,形状 [3584, 1](无 bias)—— 所以参数量恰好就是 3,584 个。 它给每个 token 算出一个标量,过 sigmoid 压到 (0, 1), 再拿这个标量去整体缩放共享专家的输出: 

  y_shared = SharedExpert(x)              [3584]   共享专家算出来的向量
  g        = sigmoid(x @ W_sg)            标量     范围 (0, 1)
  y_shared = g · y_shared                 [3584]   整条向量同乘一个数

  out = Σ wᵢ · Expert_idx[i](x)  +  y_shared
        └── 路由部分,权重来自 router ──┘     └ 共享部分,幅度由 g 控制

换句话说,它是共享专家的一个"音量旋钮" —— 模型逐 token 地决定"这个 token 要多依赖通用能力、多依赖被选中的那 8 个专家"。 g 靠近 1 就是"多听共享专家的",靠近 0 就是"几乎只听路由专家的"。

⚠️ 一个 MoE 层里有三样东西都叫"门",别混↑ 目录

三个"门"的职责完全不同
名字形状每 token 输出管什么
gate_proj (SwiGLU 内部) [3584, 20480] 20480 个数 逐通道开关,每个中间通道各开各的(就是"MLP 分支"一节讲的那个门控)
W_router [3584, 64] 64 个数 → top-8 softmax 竞争,决定选谁以及各自权重 wᵢ
W_sg (shared_expert_gate) [3584, 1] 1 个数 共享专家整体的幅度,不竞争、不选择

softmax 会互相抢,sigmoid 不会

三者的关键区别在激活函数:router 用 softmax,64 个分数互相抢、加起来受约束; W_sg 用 sigmoid,只有一个数,不和任何人比较, 所以共享专家的系数和那 8 个 wᵢ 不在同一个归一化体系里 —— 它是独立叠加上去的一项,这也正是"共享"的含义。

这个门省不了任何计算

router 的 top-8 是结构性稀疏:没被选中的 56 个专家,三个矩阵一次都不读、不算。 而 W_sg 是算完之后再乘的 —— g 哪怕是 0.01, 共享专家那 220 M 参数照样已经全部读过、全部乘过了。

所以它只影响输出的幅度,不影响 FLOPs、不影响带宽, 也就不改变上面那笔 440,634,880 的账。 下面那条"稠密尾巴"说的就是这件事:门可以关小,但活已经干完了。

成本方面它可以忽略:全部 28 层的 W_sg 加起来 28 × 3584 = 100,352 个参数, 只占共享专家的 0.0016% —— 但它是 220,204,544 结尾那个 544 的由来, 也是速查公式里 3·d·sf + d 末尾那个 d。

拿 20480 去除 18944,表里那两个倍数就对上了

上面那张表的最后两个倍数不是另算的,它们就是中间维的比值 —— 因为 SwiGLU 的参数量恒为 3 · d · f,而两个模型的 d 一样: 

  激活宽度   20480 + 20480 = 40960   ÷ 18944 = 2.16×   ← FFN 激活/层
  全量宽度   2560×64 + 20480 = 184320  ÷ 18944 = 9.73×   ← FFN 块合计/层

router 那 229,376 个参数没有"中间维"可言,但它只占 0.05%, 不影响这两个倍数的两位小数。

也就是说:把共享专家算进去之后,一个 token 在 MoE 里走的 FFN 比稠密 7B 还宽一倍多。 共享专家自己一个人就比整个 Qwen2.5-7B 的 MLP 宽 (20480 / 18944 = 1.08×) —— 所以 MoE 的激活量大于稠密 7B,不是小于。

共享专家在工程上是个"稠密尾巴"

路由专家每个 token 只激活 8/64,可以做专家并行(EP)、可以按需搬参数; 而共享专家那 220 M 参数 每个 token 都要读, 行为上和稠密层一模一样 —— 既不能跳过,也不能靠稀疏省掉。

换算成带宽:全部 28 层的共享专家共 6.17 B 参数 = 12.3 GB(BF16), 占到了 14.25 B 激活量的 43%。 它是 decode 带宽账上一块完全无法稀疏化的固定开销 —— 这也是 Qwen3 直接把共享专家去掉、改成"专家更多更小"的一个现实动机。

10.2路由这一步到底在算什么↑ 目录

# 输入:一个 token 的隐藏向量 x,形状 [3584]

logits  = x @ W_router          [3584] @ [3584, 64] → [64]
probs   = softmax(logits)                            → [64]  和为 1
idx, w  = topk(probs, k=8)                           → 8 个专家 id + 8 个权重

# Qwen2 的 norm_topk_prob = false → 直接用原始的 8 个概率当权重(和 < 1)
# Qwen3 的 norm_topk_prob = true  → 把这 8 个重新归一化成和为 1

y = Σ  wᵢ · Expert_idx[i](x)        i = 1..8
  + SharedExpert(x) · sigmoid(x @ W_sg)   ← Qwen2 特有

# 每个 Expert 内部就是上一节那个 SwiGLU,只是 ffn 从 18944 缩到 2560:
#   gate = x @ Wg[3584,2560] ;  up = x @ Wu[3584,2560]
#   h    = SiLU(gate) ⊙ up
#   out  = h @ Wd[2560,3584]

那个 Σ 和 + 号:9 路结果就是简单按位相加↑ 目录

式子里的求和不带任何花样 —— 没有拼接、没有再过一个融合矩阵、也没有重新归一化, 就是逐元素加法。展开写清楚: 

  E₁(x) · w₁      [3584]
  E₂(x) · w₂      [3584]
     ...
  E₈(x) · w₈      [3584]
━━━━━━━━━━━━━━━━━━━━━━━━━  逐位相加(8 路)
  routed          [3584]
  shared · g      [3584]
━━━━━━━━━━━━━━━━━━━━━━━━━  再逐位相加一次
  y               [3584]   ← MoE 块的输出

# 也就是 9 个 [3584] 向量的一次线性组合,系数是 w₁..w₈ 和 g。

为什么"能"相加:所有专家都吐回同一个 3584 维空间

这不是巧合,是结构决定的。每个专家的最后一步 down_proj 都是 [·, 3584] —— 中间维不管是路由专家的 2560 还是共享专家的 20480, 出口一律映射回 3584。

所以这 9 个向量住在同一个坐标系里,逐位相加才有意义。 这也正是 MoE 能做到"只换 FFN、不动其它任何东西"的原因 —— 对残差流来说,MoE 块和一个普通 MLP 的接口完全一样:进 3584,出 3584。

⚠️ 加完之后不做归一化,幅度是"自由"的

这一点容易想当然。Qwen2 的 norm_topk_prob = false, 那 8 个 wᵢ 是 softmax 的原始概率, 加起来通常小于 1(top-8 只占 64 个概率里的一部分); 而共享专家那一项的系数 g 又是完全独立的 sigmoid。

两边的幅度都不再重新缩放 —— 最终 y 的模长由训练自己去学平衡, 没有任何一步强行把它拉回某个量级。 Qwen3 把 norm_topk_prob 改成 true, 就是把路由那半边先归一化成和为 1,让幅度稳定一些; 代价是丢掉了"router 有多确信"这个信息。

别忘了残差:一层其实是 10 项相加

上面那个 y 只是 MoE 块的输出,它回到残差流还要再加一次: 

  x = x + Attention(RMSNorm(x))
  x = x + MoE(RMSNorm(x))
          └─ 这里面已经是 8 路由 + 1 共享 的和了

所以从残差流的角度看,一层 MoE 实际是 10 项逐位相加: 1 残差 + 8 路由 + 1 共享。

这些加法的开销可以直接忽略

每层每 token 大约 17 × 3584 ≈ 6.1 万 次运算 (8 次缩放 + 7 次加 + 共享的 1 缩放 1 加), 对比这一层 2 × 440.6 M = 881 MFLOP 的矩阵乘, 只有 0.007%。

和前面"非矩阵乘开销"那张表得到的是同一个结论: 凡是逐元素的操作,在 FLOPs 账上都不用记。 真正贵的永远是矩阵乘和它要读的权重。

router 是"硬"选择,但梯度是"软"传的

topk 本身不可导。训练时梯度通过权重 wᵢ 回传到路由器 —— 被选中的专家如果表现好,它的 wᵢ 会被推高,下次更容易被选中。 没被选中的专家这一步拿不到任何梯度。

这带来一个经典问题:富者愈富。少数专家被反复选中、越练越好, 其余专家饿死。所以训练时必须加负载均衡损失(load balancing loss), 强行把路由分布推向均匀。这也是推理时可以近似假设"均匀路由"的原因 —— 下面那张表就建立在这个假设上。

结合本系列压测的结论:decode 在小 batch 是访存瓶颈、大 batch 转向算力瓶颈。 所以 MoE 的收益曲线是:小 batch 省访存(但那时本来就不缺算力)、 大 batch 省算力(而那时正好卡在算力上) —— 两头都踩在点上,这才是 MoE 真正划算的地方。

10.5另外两件必须知道的事↑ 目录

  • 全部专家都必须常驻显存。 你没法只加载 8 个 —— 下一个 token 就可能路由到别的 8 个。 所以 57.41 B × 2 B = 114.8 GB 的权重一个字节都省不掉, 单张 4090 装不下。MoE 省的是算力和带宽,不是容量。
  • 负载不均会直接变成延迟长尾。 真实路由不会完美均匀, 某个专家被大量 token 选中时,那一步就得等它算完。 多卡部署时专家分散在不同卡上(expert parallelism), 负载不均还会变成卡间等待。这是 MoE 服务最主要的工程难点。

Qwen3 的一个精巧设计:激活宽度恰好等于稠密对照组

Qwen3-30B-A3B 的 moe_intermediate_size = 768, 每 token 选 8 个 —— 768 × 8 = 6144, 而它自己 config.json 里的 intermediate_size 正是 6144。

注意 lm_head 要算进去 —— 它是真矩阵乘,每个解码步都要跑。 详细推导见上文"FLOPs 是怎么数出来的"。

11.1如果 config 里有 num_experts,再套这三条↑ 目录

e  = num_experts          k  = num_experts_per_tok
mf = moe_intermediate_size          sf = shared_expert_intermediate_size(没有就当 0)

MoE 块/层
  router   = d·e
  专家全量 = e·3·d·mf
  共享     = 3·d·sf + d          (有共享专家才算,末尾的 d 是它的门)
  ────────────────────────────────────────────────
  参数     = d·e + e·3·d·mf + 3·d·sf + d
  激活     = d·e + k·3·d·mf + 3·d·sf + d

FLOPs/token = 2 × 激活参数量        ← 与 batch 无关,恒定

一个解码步真正要读的权重(batch = B,均匀路由假设)
  触及专家数 ≈ e · (1 − (1 − k/e)^B)
  权重字节   ≈ (常驻部分 + 触及专家) × dtype_bytes
             B 大到 e·(1−(1−k/e)^B) → e 时,访存优势归零

KV Cache    与 MoE 【完全无关】,仍是 2·L·kv·hd·dtype_bytes

三个不变量

换成 MoE 之后,注意力的形状、KV Cache 的单价、残差流的宽度三样一个都不变。 所以本文前七节算出来的 KV 容量公式、并发上限、抢占阈值, 对 MoE 模型原样适用 —— 变的只有权重体积和 FLOPs 这两栏。
