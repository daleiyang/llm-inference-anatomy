术语先把这六个主线指标定义清楚

下面这些缩写在正文里会反复出现,它们不是同义词 —— 每一个量的是流水线上不同的一段,彼此之间还有确定的换算关系。 本轮负载:1024 输入 / 256 输出 · 并发 1 → 64。 其余指标(MBU、MFU、KV 占用、preemption 等)只在用到它的那一节就地解释,不必现在记。 

  t=0   客户端发出请求
        │
        │  [1] 排队 queue_time —— 在 waiting 队列里等调度器放行
        │  [2] prefill —— 把 1024 个输入 token 一次算完,写进 KV Cache
        │  [3] 前端 + IPC —— 分词、HTTP、API server 与引擎之间的通信
        │

  # 吞吐 = 所有请求的输出 token 总数 ÷ 整段测试的墙钟时间(不是 1/TPOT)
贯穿全文的六个主线指标 · 最后一列是本轮的实测范围
指标中文量的是什么本轮实测
TTFT
Time To First Token		首字延迟从客户端发出请求,到收到第 1 个输出 token。它包含排队 + prefill + 前端开销三段,不含后续解码。102 ms(C=1)→ 787 ms(C=64)
ITL
Inter-Token Latency		token 间隔相邻两个输出 token 之间的时间。一条 256 token 的请求有 255 个 ITL 样本 —— 样本量大,所以它的 p99 最能暴露抖动。15.83 → 22.50 ms(p50)
ITL p99间隔的尾部把所有 ITL 样本排序后第 99% 那个值。一次卡顿只影响少数间隔,均值和中位数都看不出来,只有 p99 会跳。16.3 → 207.6 ms
TPOT
Time Per Output Token		每输出 token 耗时一条请求"首 token 之后"的平均出字速度,即 (E2EL − TTFT) ÷ (输出 token 数 − 1)。数值上就是这条请求 ITL 的均值。15.83 → 43.41 ms
E2EL
End-to-End Latency		端到端时延从发出请求到收到最后一个 token 的总时间。恒等式:E2EL = TTFT + (输出数−1) × TPOT。4,138 → 11,779 ms
输出吞吐
output token/s		用户拿到的单位时间产出的输出 token 数。这是用户真正感知的产能。61.9 → 1,387.8 tok/s

三个最容易混的地方

1 · TPOT 和 ITL 均值是同一件事的两种算法。 TPOT 是"每条请求先算自己的平均,再对请求取中位数";ITL 均值是"把所有间隔倒在一起平均"。 负载均匀时两者几乎相等(本轮 C=1 都是 15.83 ms), 有长尾时会分开 —— 两者一分开,就说明存在少数被拖长的间隔。

2 · 看 p50 得不出任何关于抖动的结论。 一次 200 ms 的停顿混在 25 万个间隔里,对中位数毫无影响,对均值影响也很小。 本系列反复出现的一条经验:抖动只在 p99 上露头; 而抢占这种更稀有的事件(万分之一量级)连 p99 都够不着,只能看专门的计数器。

3 · 吞吐不是 1 / TPOT。 TPOT 是单条请求的出字速度,吞吐是整台机器的产能 —— 后者约等于前者乘以并行的请求条数。 并发提高时 TPOT 会变差而吞吐会变好,这正是压测要权衡的那个交换。

结论拐点仍然在 C=8 到 C=16 之间

吞吐一路涨到 C=64 都没有真正饱和,但"每多给一个并发槽换来多少 token/s"从 C=8 起就掉得很快。 真正划线的不是吞吐曲线,是 ITL 的尾部 —— 它在 C=8 那一点突然裂开。 池子比第一轮宽松得多,这个拐点一步都没动:它不是被显存卡住的,是被调度器卡住的。

推荐运行点

C = 16  ·  681 tok/s

吞吐达到单流的 11.0 倍,p50 ITL 仍只有 17.2 ms(比单流慢 8.9%),p99 TTFT 1.41 秒。 再往上走,C=32 多拿 50.7% 吞吐,代价是 p99 TTFT 翻一倍到 2.85 秒。

曲线吞吐与延迟的兑换率

横轴是实际产出的 token/s,纵轴是 p99 首字延迟(对数)。曲线越往右越贵 —— 从 C=1 走到 C=16 花了 1.30 秒 p99 TTFT 买到 11 倍吞吐;从 C=32 走到 C=64 只多买到 35% 吞吐,却付出了 3.07 秒。

效率并发翻倍,吞吐没有翻倍

双对数坐标下,理想线性扩展是一条直线。实测曲线从 C=4 开始明显偏离, 到 C=64 时只剩理想值的 35.1%。

每多一个并发槽,还能换来多少

这是判断拐点最直接的量。第一个并发槽带来 61.9 tok/s,到 C=32→64 那一段, 每个槽只剩 11.3 tok/s —— 边际收益衰减到五分之一以下。 而这一段的 KV 池占用才刚过一半,掉下来的不是显存,是并行度本身的收益。

两堵墙MBU 下滑、MFU 上扬,交点在 C≈44

上一节留了个问题:并发翻 64 倍,吞吐只兑现了理想值的 35.1%,那损失掉的到底是什么? 这一节用服务端计数器正面回答 —— 不是浪费,是瓶颈换了一堵墙。 本轮给服务端加了 --enable-mfu-metrics,它把每次迭代的 FLOPs 和读取字节数累加进 /metrics, 除以窗口墙钟就得到实际算力和实际带宽,再除以 4090 的峰值(165.2 TFLOP/s FP16 累加、 1008 GB/s)就是 MFU 和 MBU。

MBU(带宽利用率)= 实际读取字节 ÷ 墙钟 ÷ 1008 GB/s。解码是访存密集的:每出一个 token,整份权重都要过一遍 HBM ——MBU 高说明卡在"读得不够快"这堵墙上。 MFU(算力利用率)= 实际浮点乘加 ÷ 墙钟 ÷ 165.2 TFLOP/s。批越大,同一份权重服务的 token 越多,GEMM 越"方",算力才用得起来 ——MFU 高说明卡在"算得不够快"这堵墙上。 中间的传动杆是 tok/iter:一次前向里被一起算掉的 token 数(解码 token + chunked prefill 切进来的块)。权重只读一次,却服务了这么多 token —— 这就是两者此消彼长的直接原因。

用 roofline 给每个并发点算一条地板

上面那张表是"实际跑到了多少",这里换个方向问:理论上最快能到多少。 解码一步至少要把权重完整读一遍、再把每条在跑的请求的 KV 读一遍, 这些字节除以峰值带宽,就是这一步的时间下限。

这张表是"批处理几乎不要钱"的直接证据

地板本身从 14.09 涨到 18.22 ms(+29%),因为要多读 63 条 KV (63 × 0.066 GB = 4.16 GB); 实测从 15.83 涨到 22.50 ms(+42%)。多出来的 13 个百分点是调度和 kernel 效率的损耗。 换句话说:并发翻 64 倍,理论代价 29%,实付 42%。 同一把尺子量 llama.cpp 的结果见《llama-cpp-压测》,差距是数量级的。

断点ITL 的尾部在 C=8 裂开

这是整轮压测里最值得看的一张图,也是"P99 ITL 才暴露抖动"这句话最干净的实证。 p50 ITL 从 C=1 到 C=64 只从 15.8 ms 涨到 22.5 ms —— 涨了 42%,温和得看不出问题。 但 p99 ITL 在 C=8 那一点从 17.6 ms 直接跳到 102.1 ms,比上一档翻了 5.8 倍。

这不是抢占,而且这一轮尤其不可能是

抢占(preemption)指 KV 池装不下时,调度器把某条正在跑的请求踢回队列 —— 它已算出的 KV 被丢弃、恢复时要重算 prefill。计数器 vllm:num_preemptions_total 全程 0 次(vLLM V1 不为它打日志行,只能从 /metrics 读)。 Waiting(队列里等的请求数;它与 Running——正在解码的请求数——之和 等于客户端在飞的并发)确实出现过 —— C=64 那一档起步瞬间排到 55 条 —— 但那是客户端一次性投放 64 条造成的,5 秒内就排空了, 稳态下 90% 的采样点 Waiting 都是 0。

更关键的是:这一轮 C=64 的 KV 池占用只有 67.5%, 离抢占阈值差得很远。同样的 ITL 裂口在池子宽松 38% 的机器上原样重现, 基本排除了"KV 紧张导致抖动"这条解释。

真正的原因是 enable_chunked_prefill: 新请求的 prefill 被切块后混进正在解码的批次。 对已经在解码的请求来说,那一步要等 prefill 块算完,于是出现一个 100–200 ms 的停顿。 C=64 时 p90 ITL 已达 187.5 ms —— 超过一成的 token 间隔卡在别人的 prefill 上。

这些停顿最终反映在端到端时间上

天花板真实并发上限是 93 条,不是 --max-num-seqs 写的 128

服务端启动参数写的是 --max-num-seqs 128,但那只是名义上限。 实际能同时跑多少条,由 KV cache 池除以单请求占用决定。 KV 占用(计数器 gpu_cache_usage_perc)就是这个池子的使用率 —— 池子大小 = 显存扣掉权重与激活之后的余量,由启动日志给出,每 token 占 56 KiB。 这一轮的池子比第一轮宽松不少,上限也跟着抬了同样的比例。

这一轮 C=64 根本没碰到 KV 墙

显存账:权重 + non-torch 14.49 GiB,峰值激活 0.26 GiB,CUDA Graph 0.34 GiB, KV 池 6.41 GiB,合计 21.50 GiB。而 --gpu-memory-utilization 0.90 给出的预算是 21.16 GiB,卡上总共有 23.52 GiB。

下一步该改什么

  • C=96 现在才是该补的点。这一轮 C=64 只用掉 68% 的池子, C=96 需要 122,880 tokens、刚好压满 120,064 —— 那才是第一次能看到 preemption 的地方。 第一轮想测这个点必须先扩池,这一轮不用。
  • 池子还能再扩一次。加 --kv-cache-memory=8471115264, 6.41 → 7.89 GiB,上限 93 → 115 条。仍然是纯赚不赔的改动,只是没有第一轮那么急迫。
  • ITL 抖动想压下去,调 --max-num-batched-tokens。 调小 → prefill 块更细 → ITL 尖峰更矮,但 TTFT 会变差。这是一个明确的对换, 取决于你的场景是流式聊天(在意 ITL)还是批量任务(在意 TTFT)。 这一轮已经证明它跟 KV 余量无关,所以只能从这里下手。
  • 跨轮对照要锁住 KV 池。两轮之间池子差得远,任何"并发上限"类的结论 都不能直接比。要比就用 --kv-cache-memory 把两边钉死在同一个数上。
  • TTFT 的 p99 在 C≤8 不要单独引用。它的样本量就是请求数 (40/60/80/120),算 p99 等于取最慢的那一两条。 ITL 的 p99 不受此限 —— 每条请求贡献 255 个间隔样本,C=8 已有 30,600 个。这正是本报告用 ITL p99、而不是 TTFT p99 来划拐点的原因。
