术语先把这六个主线指标定义清楚

下面这些缩写不是同义词: 每个指标量流水线上不同的一段,彼此之间有确定的换算关系。 本轮负载:1024 输入 / 256 输出 · 并发 1 → 64。 其余指标(MBU、MFU、KV 占用、抢占等)在用到的那一节再解释。 

  t=0   客户端发出请求
        │
        │  [1] 排队 queue_time —— 在 waiting 队列里等调度器放行
        │  [2] prefill —— 把 1024 个输入 token 一次算完,写进 KV Cache
        │  [3] 前端 + IPC —— 分词、HTTP、API server 与引擎之间的通信
        │
  ━━━━━ [1]+[2]+[3]       = TTFT 首字延迟 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
        │
        │      第 1 个输出 token 送达
        │
        │  [4] ITL × 255 —— 相邻两个输出 token 之间的间隔
        │     这 255 个间隔的平均值 = TPOT
        │
  ━━━━━ [1]+[2]+[3]+[4]   = E2EL 端到端时延 ━━━━━━━━━━━━━━━━━━━━━━━━━

  # 恒等式:E2EL = TTFT + 255 × TPOT
  # 吞吐 = 所有请求的输出 token 总数 ÷ 整段测试的墙钟时间(不是 1/TPOT)
贯穿全文的六个主线指标 · 最后一列是本轮的实测范围
指标中文量的是什么本轮实测
TTFT
Time To First Token		首字延迟从客户端发出请求,到收到第 1 个输出 token。它包含排队 + prefill + 前端开销三段,不含后续 decode。102 ms(C=1)→ 787 ms(C=64)
ITL
Inter-Token Latency		token 间隔相邻两个输出 token 之间的时间。一条 256 token 的请求有 255 个 ITL 样本。样本量大,所以它的 p99 最能暴露抖动。15.83 → 22.50 ms(p50)
ITL p99间隔的尾部把所有 ITL 样本排序后第 99% 那个值。一次卡顿只影响少数间隔,均值和中位数看不出来,只有 p99 会跳。16.3 → 207.6 ms
TPOT
Time Per Output Token		每输出 token 耗时一条请求在第 1 个 token 之后的平均出字速度,即 (E2EL − TTFT) ÷ (输出 token 数 − 1)。数值上就是这条请求 ITL 的均值。15.83 → 43.41 ms
E2EL
End-to-End Latency		端到端时延从发出请求到收到最后一个 token 的总时间。恒等式:E2EL = TTFT + (输出数−1) × TPOT。4,138 → 11,779 ms
输出吞吐
output token/s		用户拿到的单位时间产出的输出 token 数,即用户感知到的产能。61.9 → 1,387.8 tok/s

三个最容易混的地方

1 · TPOT 和 ITL 均值是同一件事的两种算法。 TPOT 是每条请求先算自己的平均,再对请求取中位数;ITL 均值是把所有间隔放在一起平均。 负载均匀时两者几乎相等(本轮 C=1 都是 15.83 ms)。 两者一分开,就说明存在少数被拖长的间隔。

2 · p50 不能说明抖动。 一次 200 ms 的停顿混在 25 万个间隔里,对中位数没有影响,对均值影响也很小。 本系列反复验证的经验是:抖动只在 p99 上露头。 抢占这种更稀有的事件(万分之一量级)连 p99 都反映不出来,只能看专门的计数器。

3 · 吞吐不是 1 / TPOT。 TPOT 是单条请求的出字速度,吞吐是整台机器的产能,约等于单条请求的出字速度乘以并行的请求条数。 并发提高时 TPOT 变差、吞吐变好,这正是压测要权衡的交换。

结论拐点仍然在 C=8 到 C=16 之间

KV 池比第一轮宽松得多,但拐点没有移动:限制拐点的是调度器,不是显存。 吞吐到 C=64 仍没有饱和,但每个新增并发槽换来的 token/s 从 C=8 起快速下降。 划出拐点的是 ITL 的尾部,不是吞吐曲线:ITL 尾部在 C=8 突然裂开。

推荐运行点

C = 16  ·  681 tok/s

曲线吞吐与延迟的兑换率

曲线越往右,每份吞吐的延迟代价越高。 从 C=1 到 C=16,p99 TTFT 增加 1.30 秒,吞吐变成 11 倍;从 C=32 到 C=64, 吞吐只多 35%,p99 TTFT 却增加 3.07 秒。 横轴是实际产出的 token/s,纵轴是 p99 TTFT(对数)。

效率并发翻倍,吞吐没有翻倍

实测吞吐从 C=4 开始明显偏离理想线性扩展,到 C=64 只有理想值的 35.1%。 双对数坐标下,理想线性扩展是一条直线。

每多一个并发槽,还能换来多少

边际吞吐是判断拐点最直接的量:它衰减到了五分之一以下。 第一个并发槽带来 61.9 tok/s,C=32→64 这一段每个槽只剩 11.3 tok/s。 这一段的 KV 池占用刚过一半,所以下降的原因不是显存,而是并行度本身的收益在减少。

两堵墙MBU 下滑、MFU 上扬,交点在 C≈44

并发是 64 倍,吞吐只有理想值的 35.1%。服务端计数器显示,差额不是浪费,而是瓶颈换了一堵墙。 本轮给服务端加了 --enable-mfu-metrics,它把每次迭代的 FLOPs 和读取字节数累加进 /metrics。 累计量除以窗口墙钟,得到实际算力和实际带宽;再除以 4090 的峰值(165.2 TFLOP/s FP16 累加、 1008 GB/s),就是 MFU 和 MBU。

  • MBU(带宽利用率)= 实际读取字节 ÷ 墙钟 ÷ 1008 GB/s。 MBU 高,说明卡在"读得不够快"这堵墙上。decode 是访存密集的:每出一个 token,整份权重都要从显存读一遍。
  • MFU(算力利用率)= 实际浮点乘加 ÷ 墙钟 ÷ 165.2 TFLOP/s。 MFU 高,说明卡在"算得不够快"这堵墙上。batch 越大,同一份权重服务的 token 越多,GEMM 越"方",算力才用得起来。
  • tok/iter 连接这两者:它是一次前向里一起算的 token 数(decode token + chunked prefill 切进来的块)。权重只读一次,却服务了这么多 token,这是两者此消彼长的直接原因。

并发是 64 倍,理论代价 29%,实付 42%。 地板从 14.09 涨到 18.22 ms(+29%),因为要多读 63 条 KV (63 × 0.066 GB = 4.16 GB)。 实测从 15.83 涨到 22.50 ms(+42%),多出的 13 个百分点是调度和 kernel 效率的损耗。 用同一方法量 llama.cpp 的结果见《llama-cpp-压测》,差距是数量级的。

断点ITL 的尾部在 C=8 裂开

这张图最直接地证明了"只有 P99 ITL 才暴露抖动"。 p50 ITL 从 C=1 到 C=64 只从 15.8 ms 涨到 22.5 ms,涨幅 42%,看不出问题。 p99 ITL 却在 C=8 从 17.6 ms 跳到 102.1 ms,是上一档的 5.8 倍。

这不是抢占,而且这一轮尤其不可能是

抢占计数器 vllm:num_preemptions_total 全程 0 次。 抢占指 KV 池装不下时,调度器把一条运行中的请求退回队列:它已算出的 KV 被丢弃,恢复时要重算 prefill。 vLLM V1 不为抢占打日志行,只能从 /metrics 读。

队列等待只出现在起步阶段,约 6 秒内就排空了。 Waiting 是队列里等待的请求数,Running 是正在 decode 的请求数,两者之和等于客户端在飞的并发。 C=64 那一档起步瞬间 Waiting 排到 55 条,原因是客户端一次性投放 64 条。 稳态下 90% 的采样点 Waiting 是 0。

更关键的是,这一轮 C=64 的 KV 池占用只有 67.5%,离抢占阈值很远。 同样的 ITL 裂口在 KV 池宽松 38% 的机器上原样重现, 基本排除了"KV 紧张导致抖动"这个解释。

真正的原因是 enable_chunked_prefill: 新请求的 prefill 被切块后混进正在 decode 的 batch。 已经在 decode 的请求要等 prefill 块算完,于是出现一次 100–200 ms 的停顿。 C=64 时 p90 ITL 已达 187.5 ms,即超过一成的 token 间隔卡在别人的 prefill 上。

这些停顿最终反映在端到端时间上

天花板真实并发上限是 93 条,不是 --max-num-seqs 写的 128

--max-num-seqs 128 只是名义上限。 实际能同时跑多少条,由 KV 池大小除以单请求占用决定。 KV 池大小 = 显存扣掉权重与激活之后的余量,由启动日志给出,每 token 占 56 KiB。 KV 占用(计数器 gpu_cache_usage_perc)是 KV 池的使用率。 这一轮的 KV 池比第一轮宽松,上限也按同样的比例提高。

这一轮 C=64 没有碰到 KV 墙

显存账:权重 + non-torch 14.49 GiB,峰值激活 0.26 GiB,CUDA Graph 0.34 GiB, KV 池 6.41 GiB,合计 21.50 GiB。--gpu-memory-utilization 0.90 给出的预算是 21.16 GiB,卡上总共有 23.52 GiB。

这批数据能不能信:四条自检

  • 每请求输出 token 正好是 256(全部 7 档),说明 --ignore-eos 生效, 各档的工作量相同。吞吐差异不可能来自"有的请求提前停了"。
  • --temperature 0 生效:sweep 日志里没有 no longer sets temperature==0 这句 WARNING(Round 1 每档都有)。 采样路径与 llama.cpp 侧同构。
  • prefix caching 关着:启动日志 non-default args 里是 enable_prefix_caching: False。KV 使用率随并发严格线性 (0.9 / 1.9 / 3.7 / 7.4 / 14.1 / 28.9 / 57.2 %),没有缓存命中造成的塌陷。 《vllm-03-KV的线性》把这条线性关系单独做成了实验,那边的对账更严格。
  • 零失败、零抢占:1,332 条请求全部成功, vllm:num_preemptions_total 全程为 0。本轮没有一个点触到 KV 上限。

下一步该改什么

  • 下一个该补的点是 C=96。这一轮 C=64 只用掉 68% 的 KV 池, C=96 需要 122,880 tokens,刚好压满 120,064,是第一个能看到抢占的点。 第一轮要测这个点必须先扩 KV 池,这一轮不用。
  • KV 池还能再扩一次。加 --kv-cache-memory=8471115264, 6.41 → 7.89 GiB,上限 93 → 115 条。这仍是只有好处的改动,只是没有第一轮那么急。
  • 要压低 ITL 抖动,调 --max-num-batched-tokens。 调小 → prefill 块更细 → ITL 尖峰更矮,但 TTFT 会变差。这是明确的取舍: 流式聊天在意 ITL,批量任务在意 TTFT。 这一轮已证明抖动与 KV 余量无关,所以只能从这里下手。
  • 跨轮对照要锁住 KV 池。两轮的 KV 池相差很大,"并发上限"类的结论 都不能直接比。要比,就用 --kv-cache-memory 把两边固定在同一个值。
  • 不要单独引用 C≤8 的 TTFT p99。它的样本量就是请求数 (40/60/80/120),p99 等于最慢的那一两条。 ITL 的 p99 不受此限:每条请求贡献 255 个间隔样本,C=8 已有 30,600 个。所以本报告用 ITL p99 而不是 TTFT p99 来划拐点。
