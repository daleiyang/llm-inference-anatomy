术语先把这七个指标定义清楚

下面这些缩写在正文里会反复出现,它们不是同义词 —— 每一个量的是流水线上不同的一段,彼此之间还有确定的换算关系。 本轮负载:1024 输入 / 256 输出 · 并发 1 → 64 · 两个引擎各扫一遍。两个引擎的指标口径由同一个客户端(vllm bench serve)统一测量,所以 TTFT / ITL / E2EL 这几个数是可比的。服务端侧的计数器(KV 占用、抢占、running/waiting)只有 vLLM 有,llama.cpp 只暴露 slot,所以本报告的所有对照都建立在客户端指标上。

三个最容易混的地方

1 · TPOT 和 ITL 均值是同一件事的两种算法。 TPOT 是"每条请求先算自己的平均,再对请求取中位数";ITL 均值是"把所有间隔倒在一起平均"。 负载均匀时两者几乎相等,有长尾时会分开 —— 两者一分开,就说明存在少数被拖长的间隔。 本轮 C=1 两个引擎都是均匀的(vLLM 15.83 / 15.83,llama.cpp 5.84 / 5.83); 到 C=8 llama.cpp 就分成了 10.30 / 18.33,而 vLLM 还是 16.63 / 18.25。

2 · 看 p50 得不出任何关于抖动的结论。 一次 200 ms 的停顿混在 25 万个间隔里,对中位数毫无影响,对均值影响也很小。 本系列反复出现的一条经验:抖动只在 p99 上露头; 而抢占这种更稀有的事件(万分之一量级)连 p99 都够不着,只能看专门的计数器。

3 · 吞吐不是 1 / TPOT。 TPOT 是单条请求的出字速度,吞吐是整台机器的产能 —— 后者约等于前者乘以并行的请求条数。 并发提高时 TPOT 会变差而吞吐会变好,这正是压测要权衡的那个交换。

结论量化省的是字节,省不了调度

llama.cpp 把每步要读的权重从 14.1 GB 压到 4.7 GB,单流解码因此快了 2.71 倍 —— 这一段是实打实的,字节账能算到小数点后两位。 但并发一上去,优势就被吃光:两条吞吐曲线在 C≈8 就换位了, 而不是第一轮估计的 C≈21。原因不在算力,在批处理红利: vLLM 在 C=64 仍能吃到理论地板的 81%,llama.cpp 只剩 25%。

第一轮的三条数据瑕疵,两条已消除、一条大幅改善

第一轮的对照有三个问题:① llama.cpp 的 prompt cache 默认开着,C=32 有 23% 的请求白拿了 prefill; ② C=32 掉了 8 条请求;③ 只测了 1 / 8 / 32 三个点。 本轮 ① 已用 --cache-ram 0 --slot-prompt-similarity 0 关掉, ③ 补齐到 7 个点,② 改善到只掉 1 条(C=32,319/320)。 所以这一轮的交叉点 C≈8 比第一轮的 C≈21 更可信 —— 第一轮那个数是被 prompt cache 抬高的。

显存这一项本轮也补上了:nvidia-smi 实测 19,089 MiB,与权重加 KV 的推算差 1.5%。

交叉两条吞吐曲线在 C≈8 换位

字节账单流那 2.71 倍,能算到小数点后两位

单流解码是纯带宽问题:每生成一个 token,把整个模型的权重从显存读一遍。 量化把这堆字节压小,步长就该按同样的比例变短。这是全篇唯一一处理论与实测能对到 10% 以内的地方。 

# 每个 decode step 要读的字节
vLLM  bf16    参与矩阵乘的参数 7,070,619,136 × 2 B = 14.14 GB
              + KV(1 条 × 1152 tok × 56 KiB)      =  0.07 GB
                                                    ──────────
                                                     14.21 GB

llama Q4_K_M  Qwen2.5-7B-Instruct-Q4_K_M.gguf      =  4.68 GB
              + KV(fp16,和 vLLM 同价)             =  0.07 GB
                                                    ──────────
                                                      4.75 GB

# 字节账预测的步长比
14.21 ÷ 4.75 = 2.99 ×

# 实测
15.83 ms ÷ 5.84 ms = 2.71 ×      达成预测的 91%

# 差在哪:反推各自的实际带宽
vLLM   14.21 GB ÷ 15.83 ms = 898 GB/s  = 89% MBU
llama   4.75 GB ÷  5.84 ms = 813 GB/s  = 81% MBU

2.71 而不是 2.99,差的那 9% 是带宽效率

两边跑的是同一张卡、同一条 1,008 GB/s 的总线。 vLLM 的 decode kernel 把带宽跑到 89%,llama.cpp 的 Q4_K_M 反量化路径跑到 81% —— 解量化本身要花掉一点带宽预算(读 4-bit 权重、在寄存器里展开成 fp16 再乘)。 这 8 个百分点就是 2.99 与 2.71 之间的全部差距。

换个说法:量化没有骗人,它确实把字节数降到了 1/3; 但它换来的加速是 2.7 倍而不是 3.0 倍,因为省下的字节里有一小部分被解码开销吃回去了。

prefill 这一头,量化一点忙都帮不上

prefill 是算力密集的(第三节那张 roofline 图量过:prefill 秒能跑到 146 TF/s)。 量化省的是读权重的字节,而 prefill 的瓶颈根本不在读权重 —— 一次读进来要算 1024 个 token。所以 TTFT 这一栏,llama.cpp 从 C=1 到 C=64 没有一档赢过: 

# TTFT p50(ms),越小越好
C=1    vLLM 102   llama  93    llama 略快
C=8    vLLM 306   llama 204    llama 快(它此时批更小)
C=16   vLLM 474   llama 324
C=32   vLLM 588   llama 478
C=64   vLLM 787   llama 442

# 但这是拿吞吐换的:同一档下 llama.cpp 的 ITL 差得多
C=64   vLLM ITL 22.5 ms   llama ITL 35.3 ms

上面比的是客户端量到的 TTFT,里面含调度与网络。 换成两边服务端自己记的纯 prefill 再比一次,结论一样、幅度也一样 —— 两条独立路径同向,说明这 9% 不是测量噪声: 

# A · 服务端量到的纯 prefill(1024 tok,C=1)
llama.cpp  prompt eval           85.3 ms   日志中位数,40 条
vLLM       request_prefill_time  93.5 ms   ← llama 快 8.8%

# B · 客户端量到的 TTFT(两边都含调度与网络)
llama.cpp  TTFT p50              92.7 ms
vLLM       TTFT p50             102.3 ms   ← llama 快 9.4%

这 9% 不是量化的功劳

prefill 一次前向要算 1024 个 token,权重只读一遍就摊给了所有 token —— 瓶颈在 FLOPs 不在带宽,而 Q4_K 的解量化只会让 FLOPs 更多。 所以这 9% 来自实现细节(kernel、框架开销),不是"少读了 3 倍字节"换来的。 量化换来的是解码速度和显存,不是首字延迟 —— 对话类负载(短输入长输出)收益大;RAG / 长文摘要(长输入短输出)收益小得多。

摊薄批处理红利,vLLM 吃到 81%,llama.cpp 只吃到 25%

批处理的全部价值在于:一次读进来的权重,给批内所有请求共用。 所以并发翻倍时,单步耗时不该翻倍 —— 它只该多出"多读那些 KV"的时间。 这个"只多出 KV"的下限就是 roofline 地板,拿它去除实测步长,就得到批处理效率。

换个说法:每多接一条并发,要多付多少

# 理论地板:每多一条并发,每步多读 1152 tok × 56 KiB = 0.066 GB
0.066 GB ÷ 1,008 GB/s = 0.0655 ms / 槽位

# 实测斜率(C=1 → C=64 的 ITL 增量 ÷ 63)
vLLM       (22.50 − 15.83) ÷ 63 = 0.106 ms / 槽位   地板的 1.6 倍
llama.cpp  (35.32 −  5.84) ÷ 63 = 0.468 ms / 槽位   地板的 7.1 倍

这就是"量化省不了调度"的量化版本

llama.cpp 每多接一条并发,单步要多花 0.47 ms;vLLM 只多花 0.11 ms。 差的这 0.36 ms和权重精度毫无关系 —— 它是 PagedAttention、 continuous batching、CUDA graph 复用这些调度侧工程的价值。

这 0.36 ms 的差价,就是「交叉」那一节 C≈8 换位的全部来源。

波次10 个整整齐齐的 32:llama.cpp 没在做 continuous batching

效率掉得这么快,直接原因能从时间账上读出来。 如果引擎在做 continuous batching,一条请求结束就该立刻补进下一条, 总耗时应该远小于"批数 × 单条端到端时延"。实测正好相反。 

# llama.cpp C=32:320 条请求 ÷ 32 个槽位 = 10 批
单条 e2e p50            = 17.85 s
总耗时 ÷ 10             = 179.73 ÷ 10 = 17.97 s
                                        ──────────
                          两者相差 0.7%

# 同样的检验用在 C=64 上
单条 e2e p50            = 15.19 s
总耗时 ÷ 8              = 121.61 ÷ 8  = 15.20 s   相差 0.1%

# 对照 vLLM C=32
单条 e2e p50            = 7.96 s
总耗时 ÷ 10             = 79.79 ÷ 10  = 7.98 s   ← 也吻合,因为负载是定长齐发

这个 0.7% / 0.1% 的吻合度就是结论本身:总耗时几乎等于"批数 × 单条端到端时延", 说明新请求只在整批结束后才成批进场,每 18.0 秒一次。 如果引擎在做 continuous batching,一条结束就补一条,这种整齐的批边界根本不会存在。 换手间隙只有约 0.5 秒(= 实测 TTFT p50 478 ms),占一波的 3%。 注意本轮没有对 llama.cpp 做 1 Hz 采样, 所以这里只有时间账,没有槽位占用的实测曲线 —— 补采样是「下一步」的第 3 条。

差别在于 prefill 是切片插入还是整块插入

vLLM 开着 enable_chunked_prefill:新请求的 prompt 被切成块, 和正在进行的 decode 混在同一个 step 里,每一步只堵一小会儿。 llama.cpp 是整块插入 —— 一条新请求进来就要把所有正在解码的 slot 一起堵住, 直到它的 1024 个 token 算完。 所以 llama.cpp 在 C=4 就已经有一半解码时间在等待,vLLM 到 C=8 才 9.8%。

反常C=32 那一档塌了,而且不是噪声

C=32 那一档 81,408 步里一次都没复用,而它正是塌得最狠的一档; C=1 复用 99.22% —— 几乎每一步都命中(理论上限也就 99.6%, 因为每条请求的那一次 prefill 步本来就复用不了),正是唯一贴住 roofline 的一档。 两列几乎同起同落。 机制上也说得通:CUDA graph 把几百次 kernel launch 打包成一次提交, batch 形状一变就要重新捕获 —— vLLM 把 batch padding 到固定的几个桶, 任何实际 batch 都能命中已捕获的图;llama.cpp 的活跃 slot 数每步都在变(30/31/32 来回跳), 图就一直命中不了。

但服务端日志没有解释原因(verbosity 已开到 3), 要坐实因果必须做对照实验:用 -DGGML_CUDA_USE_GRAPHS=OFF 重编一份再扫一遍 —— 如果关掉图之后 C=1 大幅变慢而 C=32 几乎不变,因果链就闭合了。

另外两条线索

② 唯一一条失败请求也出在这一档(319/320)。

③ 排除项:不是显存(llama.cpp 的 KV 池按 -c 262144 分配,C=32 只用掉一半)、 不是温度(全程 ≤73 °C)、不是 prompt cache(本轮已关)。

在补上对照实验之前,C=32 这一档不应该写进任何结论 —— 本报告的交叉点是用 C=8/16 算的,批处理效率引用的是 C=64,都绕开了这一档。

显存Q4 省下的那 10 GiB,这一轮全花在 KV 上了

量化最直观的好处是权重变小:14.49 GiB → 4.36 GiB,省下 10 GiB。 但这一轮给 llama.cpp 开了 -np 64 -c 262144(64 个槽位 × 4096 上下文), KV 池按满配分配,把省下的显存又吃回去了。

这是一个配置选择,不是引擎的性质

如果把 llama.cpp 的 -c 调成和 vLLM 一样的有效容量, 它的 KV 池会小得多,空出来的显存可以拿去开更多槽位或跑更大的模型。 Q4 的显存红利是真的,只是这一轮的启动参数没让它体现出来。

反过来说,vLLM 侧的 6.41 GiB KV 池换算成 120,064 token, 而 llama.cpp 的 262,144 token 是它的 2.18 倍 —— 在"能同时装多少上下文"这一项上,量化确实赢了, 只是本轮的负载(1280 tok/请求)根本用不到那么多。

这批数据能不能信:三条自检

  • 两个引擎的输出工作量差 1.35%,不是零。 vLLM 七档每条精确 256 个输出 token(--ignore-eos 严格生效); llama.cpp 是 250–256 不等(C=1 为 255.95,C=32 为 250.00), 七档合计 336,142 token,比 vLLM 的同口径值少 4,594 个(1.35%)。 吞吐是"输出 token ÷ 墙钟",所以 llama.cpp 侧被低估了约 1.35% —— 方向对它不利,但幅度远小于 C≥16 时 20%–57% 的差距,不影响 C≈8 这个交叉点。 做跨引擎对比时这一项必须现场核对,不能假设 --ignore-eos 在两边行为一致。
  • prompt cache 确实关着:--cache-ram 0 --slot-prompt-similarity 0, 这是第一轮那个 C≈21 交叉点被抬高的原因,本轮已消除。
  • 一条失败请求出在 C=32(319/320),而那一档恰好也是每条输出最少的 (250.00,七档最低)、CUDA graph 复用率归零的一档 —— 三个异常同源,见「反常」一节。

下一步这轮之后该补的四件事

  • C=32 的对照实验。用 -DGGML_CUDA_USE_GRAPHS=OFF 重编一次, 在 C=16 / 32 / 64 三档上重跑。如果关掉 CUDA graph 之后 C=32 的塌陷消失(或者三档一起变慢但恢复单调), 因果就定了。这是本轮唯一一个悬而未决的问题,优先级最高。
  • 把 llama.cpp 的 -c 调到和 vLLM 等效。 本轮 262,144 的上下文预算让显存对比失去意义。设成 -np 64 -c 81920(64 × 1280)再测一次,才能看到 Q4 真正的显存红利。
  • 给 llama.cpp 补一个 1 Hz 采样器。 显存已有单点实测(19,089 MiB),但功耗、槽位占用、以及显存随时间的变化仍然空白。 套一个和 vLLM 侧同样的轮询就能补齐,成本极低。
  • 补 C=4 与 C=8 之间的点。交叉点算出来在 C≈8.3, 而 C=8 正好是两条线几乎重合的地方(411 vs 416,差 1%)。 加测 C=6 和 C=12 能把这个阈值钉得更准 —— 它是"什么时候该换引擎"的实操分界线。
