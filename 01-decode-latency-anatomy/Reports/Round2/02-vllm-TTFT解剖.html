三个最容易混的地方

1 · TPOT 和 ITL 均值是同一件事的两种算法。 TPOT 是"每条请求先算自己的平均,再对请求取中位数";ITL 均值是"把所有间隔倒在一起平均"。 负载均匀时两者几乎相等(本轮 C=1 都是 15.83 ms), 有长尾时会分开 —— 两者一分开,就说明存在少数被拖长的间隔。

2 · 看 p50 得不出任何关于抖动的结论。 一次 200 ms 的停顿混在 25 万个间隔里,对中位数毫无影响,对均值影响也很小。 本系列反复出现的一条经验:抖动只在 p99 上露头; 而抢占这种更稀有的事件(万分之一量级)连 p99 都够不着,只能看专门的计数器。

3 · 吞吐不是 1 / TPOT。 TPOT 是单条请求的出字速度,吞吐是整台机器的产能 —— 后者约等于前者乘以并行的请求条数。 并发提高时 TPOT 会变差而吞吐会变好,这正是压测要权衡的那个交换。

结论TTFT 的增长几乎全部来自排队

把 TTFT 拆成"排队"和"真算"两段之后,结论很干脆:从 C=1 到 C=64, prefill 只涨了 5.1 倍,而排队从 0 涨到 380 毫秒 —— 它占 TTFT 的比重同步从 0% 升到 38%。 并发越高,用户等的越不是计算,而是别人。

分解TTFT 拆成三段

服务端的 request_queue_time 和 request_prefill_time 两个 histogram, 差分后得到每个并发点的平均排队时间与平均 prefill 时间。 两者之和与客户端观测的 TTFT 之间还差一截,那是 vLLM 前端(API server)的处理与 IPC 开销。

两个分量的增长速度完全不同

这一轮把"排队是不是 KV 逼出来的"这个问题关掉了

第一轮 C=64 时 KV 占用 93.3%、running 中位数只有 62, 当时的解释是"KV 池确实开始限制并发了"。

这一轮 KV 池大了 38%,C=64 的占用只有 67.5%,离满还差三分之一 —— 可是 running 中位数还是 61,排队还是涨到 380 ms。 同一个现象在池子宽松得多的机器上原样重现,说明它不是显存造成的, 而是请求完成与下一条 prefill 完成之间的自然空隙,加上 chunked prefill 的调度节奏。

混批每次迭代里,四份 prefill 陪着一份 decode

iteration_tokens_total 记录每次 engine 迭代处理了多少 token。 如果只有 decode,这个数应该等于正在跑的请求数。实测每 1 个 decode token 就配着约 4 个 prefill token —— 多出来的部分, 就是被 chunked prefill 切碎后塞进同一批的 prefill 块。

这是 ITL p99 尖峰最直接的物理解释:一个正在解码的请求,每一步都要等同批次里的 prefill 块算完。C=64 时每次迭代要处理 317 个 token —— decode 61 个、 prefill 256 个,于是解码方向的每一步都被拖长,尾部就出现了 200 ms 量级的停顿。 七个档位共 34,779 次迭代,这个 1 : 4 从头到尾没变过。

波形973 秒全程实况

七个并发点在时间轴上依次排开, 可以直接看到队列什么时候堆起来、KV 什么时候冲顶 —— 以及这一轮它其实没有冲顶。

功耗墙可能是效率衰减的一部分原因

C=64 时 GPU 持续运行在 447 W,而 C=1 只有 368 W。撞上功耗限制后 GPU 会降频, 这会直接压低实际可用带宽和算力 —— 而 vLLM 的任何指标都看不到这件事。 把 C=64 的效率只有 35.1% 全部归因于 prefill 抢算力是不够的,至少还要算上功耗墙这一份。

对账PagedAttention 的账,算得平不平

KV 占用不该是个测出来才知道的黑箱 —— 它应该能从并发数、序列长度、每 token 的 KV 体积三个数直接算出来。 拿稳态实测值去对,误差有多大就说明这本账理解得有多准。

先把口径分清楚

直觉公式是 并发 × (in_len + out_len) × 56 KiB ÷ 池大小。 但 in + out = 1280 是请求结束那一刻的占用, 稳态下大量请求正生成到一半,平均只占 in + out/2 = 1152。 峰值要对峰值,均值要对均值,混用会系统性高估 11%。

账算平了,而且比第一轮更平

峰值口径误差 0.00 ~ −0.72 个百分点,七个点全部落在 1 pp 以内, 前四个点更是精确到小数点后两位都不差。 均值口径在低并发下同样贴合,只有 C=64 出现 −2.69 pp 的偏差。

而这个偏差不是模型错了,是"名义并发 ≠ 实际并发"。 C=64 时 running 中位数只有 61。用 61 代入公式:预期 58.52%,实测 58.72% —— 误差 +0.20 个百分点。

这 3 条的差额是请求换手的自然空隙,不是显存约束 —— 理由见前面「分解」一节。

剩下 C=8~32 那 −0.18 ~ −1.49 pp 的小幅负偏差,来自请求生命周期错开: 理论均值假设输出进度均匀分布在 0~256 之间,但请求完成到新请求 prefill 完成之间 有短暂空隙,实际占用略低于理想值。这个方向和量级都合理。

一个这轮没暴露的坑

本例的 1280 和 1152 都能被 block_size=16 整除,对齐损耗恰好为零 —— 这是运气。做容量规划时要按 block 向上取整,不能按 token 数直接算。 非整除情形的算例见《vllm-03-KV的线性》。

复现两轮独立测试的吻合度

两轮相隔十天,换了一台实例、换了驱动版本,配置相同。 这比第一轮内部的两次重跑更能检验方法的可靠性。

为什么会有第二轮:一个被证伪的假设

重跑一轮的唯一动机,是给客户端补上 --temperature 0, 让两个引擎的采样路径同构。动手前的判断是:第一轮的 vLLM 走了模型 generation_config.json 的默认值 (temp 0.7 / top_k 20 / repetition_penalty 1.05), 而 repetition_penalty 每出一个 token 都要扫一遍已生成的历史, 是 vLLM 单方面付的成本 —— 所以第一轮的 vLLM 数据应该偏悲观, 对 llama.cpp 不公平。

这个判断是错的,必须写进结论

七个档位的差异全部落在 ±1.2% 以内,而且方向还不一致 (低并发第二轮略升、高并发第二轮略降,原因见上图 note)。这是噪声,不是信号。 repetition_penalty 1.05 对 vLLM 的吞吐没有可测量的影响。

那这一轮白跑了吗?没有 —— 它把"采样参数不同构"这个变量 从怀疑名单里划掉了。在此之前,llama.cpp 与 vLLM 之间的任何差距 都可以被质疑"是不是采样设置不一样导致的";现在这条退路没了, 剩下的差异只能归因于引擎本身。排除一个假设也是结果。 它还有一个副作用:把两轮焊成了一组可以互相印证的数据 —— 下面这段之所以敢说"复现到 1%",前提正是这两轮除机器外确实同构。

跨机器复现到 1%,但有一个数不能跨机器搬

吞吐、延迟、ITL 裂口位置、混批比例、KV 对账误差 —— 全部复现。 唯一差了 38% 的是 KV 池大小:4.64 GiB / 86,896 tok 变成 6.41 GiB / 120,064 tok。 同一条启动命令,只因为驱动从 590.48.01 换成 580.159.03, vLLM profiling 探到的已占用显存少了 1 GiB —— 凡是从 KV 池推出来的数(并发上限、抢占阈值),必须每台机器现读日志。

对照第一轮的结论,哪些站住了

被证实的

  • ITL 尾部在 C=8 裂开 —— 两轮完全一致(p99 从 17.6 跳到 102.1 ms), 而且现在有了机制层面的证据:每次迭代混入了 4 倍于 decode 的 prefill token。
  • 抢占不是原因 —— 采样器全程 969 个点,num_preemptions_total 始终为 0。
  • PagedAttention 的账完全算得平 —— 七个并发点的峰值占用 与理论预期误差全部在 0.72 pp 以内。这意味着 KV 容量可以事先算准, 不需要试出来。
  • 混批比例恒定在 1:4,与第一轮完全一致,不随并发也不随机器变化。
  • vLLM 前端开销随并发增长 —— 从 9 ms 到 141 ms,两轮同一量级。 注意这一段是残差而非直接测量,趋势成立,绝对值不宜逐毫秒引用。

被修正的

  • "C=64 时 KV 池限制了并发"这个解释不成立。 第一轮据 running 中位数 62 < 64 归因于池子不够;这一轮池子宽松得多,running 还是 61。 差额来自请求换手的空隙,跟 KV 无关。
  • "真实并发上限 67"是这台机器的数,不是这个模型的数。 同样的算法在第二轮给出 93.8。上限跟着 KV 池走,而 KV 池跟着 profiling 走。

新发现

  • MFU / MBU 计数器这次有数了。加上 --enable-mfu-metrics 之后, estimated_flops_per_gpu_total 与 estimated_read_bytes_per_gpu_total 全程有效,C=1 实测 4.16 TFLOP/s、887 GB/s —— 第一轮这两个 counter 全程为 0。

下一步三件值得做的事

  • 补测 C=96。这一轮 C=64 只吃掉 67.5% 的池子, C=96 需要 122,880 tokens、刚好压满 120,064 —— 那才是第一次能看到 preemption 的地方, 也是唯一能把"排队"和"抢占"这两件事分开看的位置。
  • 调低 --max-num-batched-tokens 再跑一轮, 验证"prefill 块变小 → ITL 尖峰变矮、TTFT 变差"这个对换关系。 现在有了 iteration_tokens 指标,可以直接量化块大小的变化。 既然已经排除了 KV,这是唯一剩下的旋钮。
  • 把 KV 池钉死再跨轮比。加 --kv-cache-memory 把两轮固定到同一个字节数,"并发上限""抢占阈值"类结论才能做真正的单变量对照。
