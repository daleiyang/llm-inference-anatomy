三个最容易混的地方

1 · TPOT 和 ITL 均值是同一件事的两种算法。 TPOT 是"每条请求先算自己的平均,再对请求取中位数";ITL 均值是"把所有间隔倒在一起平均"。 负载均匀时两者几乎相等,有长尾时会分开 —— 两者一分开,就说明存在少数被拖长的间隔。 本轮 TPOT 29.17 ms、ITL 均值 31.29 ms,已经分开了。

2 · 看 p50 得不出任何关于抖动的结论。 一次 200 ms 的停顿混在本轮这 26.2 万个间隔里,对中位数毫无影响,对均值影响也很小。 本系列反复出现的一条经验:抖动只在 p99 上露头; 而抢占这种更稀有的事件(万分之一量级)连 p99 都够不着,只能看专门的计数器。

3 · 吞吐不是 1 / TPOT。 TPOT 是单条请求的出字速度,吞吐是整台机器的产能 —— 后者约等于前者乘以并行的请求条数。 并发提高时 TPOT 会变差而吞吐会变好,这正是压测要权衡的那个交换。

结论并发旋钮拧到 64,实际只跑了 16 条

前三轮的结论是"加并发换吞吐、加长度换 KV",都还在线性区里。 这一轮越过了 KV 池的边界,线性关系全部作废: 并发参数写的是 64,服务端能同时驻留的只有 16 条(均值 15.65,峰值 19), 另外 48 条一直躺在 waiting 队列里 —— 中位数排了 169 秒才拿到第一个 token。

这一轮的对照价值在于:池子比第一轮大 38%,断崖的形状一点没变。 驻留数从 11.17 抬到 15.65(+40%,和池子的 +38% 基本同步), 但抢占依然稳定发生、TTFT 依然是三位数秒、p99 ITL 依然看不见抢占 —— 超卖的后果只跟"超了多少倍"有关,跟池子的绝对大小无关。

如果这份报告只能留一句,是这一句:重算是伤口,并发塌缩才是断崖。 38 次抢占带来的重算只吃掉全程 6.2% 的墙钟; 真正让吞吐掉六成的,是 64 条并发被 KV 池砍到只剩 16 条。

压爆不等于崩溃 —— 这是本轮最该写进结论的一条

超卖 4.4 倍、KV 顶到 100%、抢占 38 次, 结果是零失败、零错误、输出 token 一个不少 —— 128 条请求全部返回,每条精确 2,048 个输出 token。

PagedAttention 加上抢占重算,把"资源不够"翻译成了排队更久, 而不是"请求失败"或"结果不对"。 这是一个把硬失败转化成软降级的设计 —— 代价全部记在延迟上,一分没记在正确性上。 所以下面所有"断崖"的说法,指的都是延迟和吞吐的断崖,不是可用性的断崖。

锯齿抢占是一个负反馈控制环

把前 140 秒放大,能看到一个非常规整的循环,而且每一圈都长一个样: 调度器一次放进几条新请求 → KV 冲到 99.6% → 抢占一条 → KV 掉 5.2 个百分点 → 继续解码又慢慢涨回 99.6% → 再抢一条。Running 沿着 19 → 18 → 17 → 16 往下走, 直到有一批请求跑完,再一次性放进新的。

抢占事件发生时刻抢占前 KV抢占后 KV释放Running
 只列前 12 次,全部 38 次的统计见正文。「释放」为 KV 占用的下降,括号内换算成 token。

每次抢占平均释放 5.20 个百分点 = 6,242 个 token —— 正好是一条请求当时持有的上下文。 也就是说:vLLM 每次只踢一条,踢的是 running 队列末尾那条(最晚进来的), 而不是把批次砍半。这是一个非常克制的策略,代价是它必须频繁地踢。 释放量取决于请求的上下文长度,而不是池子大小。

照着核对:日志里没有 "is preempted by"

实验计划里写"server 日志里出现类似 Sequence group ... is preempted by ... 的行" —— 这一条在 vLLM V1 上不成立。服务端日志里 preempt 出现 0 次,那是 V0 引擎的日志格式。V1 只在 /metrics 里暴露 vllm:num_preemptions_total,不打任何日志行。

也就是说:如果你只看服务端日志,这 38 次抢占是完全隐形的。 能抓到它的唯一办法就是本轮用的这个 1 Hz 采样脚本。

断崖断在吞吐和 TTFT,没有断在 ITL

这是本轮最反直觉的一条。实验计划预期"P99 ITL 出现巨大尖峰(被抢占的请求要重算)", 实测 p99 ITL = 227.7 ms,和零抢占时的 197–214 ms 属于同一水位; p90 ITL 甚至好得多(24.7 ms,并发扫描 C=64 是 187.5 ms)。

原因是算术:128 条 × 2047 个间隔 = 262,016 个 ITL 样本, 抢占只制造了 38 个巨大间隔,占 0.0145% —— 落在 p99.99 上, --metric-percentiles 50,90,99 根本够不着。 而 p90 反而变好,是因为批内只剩 16 条流,别人的 prefill 抢步变少了。

这条经验值得单独记下来:p99 ITL 不是抢占的监控指标。 抢占的指标只有两个 —— num_preemptions_total 和 TTFT 尾部。 两轮独立复现,可以当结论用了。

反过来用:ITL 和 TTFT 谁在爆,直接指向两种不同的病

上面那条结论有个很实用的逆命题。线上收到"用户抱怨慢"的时候,先分清是哪一个在爆: 

ITL 正常 + TTFT 爆炸   →  容量不够,请求在排队
                        药:加卡、减并发、缩 max_model_len、上限流
                        ← 本轮就是这一种:ITL p50 23.39 ms 几乎正常,
                          而 TTFT p50 是 169 秒

ITL 也慢              →  解码本身有问题
                        药:查 batch 配置、kernel、量化实现
                        ← Test 5 里 llama.cpp 遇到的是这一种

两种病,两种药。吃错药的典型是:看到 TTFT 爆了就去换更快的卡 —— 为什么没用,见下一节。

驻留数几乎线性跟随池子,吞吐却是亚线性的

池子 +38.2% → 驻留 +40.1%(几乎 1:1,和日志预告的 +38.3% 也对得上) → 吞吐只有 +21.3%。多驻留的那 4.5 条请求,边际吞吐贡献在递减 —— 并发扫描已经量化过这件事:从 C=16 到 C=32,扩展效率就从 69% 掉到 52%。 在过载区,扩容 KV 池的收益比"能多装几条"看起来的要小。

更值得注意的是抢占次数几乎没变(37 → 38)。 这说明抢占频率是被"KV 顶满"这个状态决定的,而不是被池子的绝对大小决定的。 只要还在超卖,扩容只是让断崖挪了个位置,并没有消除它。

过载下的 TTFT 完全是排队论,和 GPU 无关

prefill 本身只要 1.10 秒。用户等的 169 秒里,有 168 秒是在等前面的人。 这个数由"队列长度 ÷ 出队速率"决定,跟卡多快、KV 多大、模型多小没有任何关系 —— 换一张 H100 也只会让那 1.09 秒变成 0.4 秒。

推论很直接:过载时唯一有效的手段是限流,不是加速。 在服务端设并发上限并对超出的请求快速失败(429), 比让它们在队列里排 169 秒有用得多 —— 后者还占着连接和客户端超时预算。

对账两个计数器打架:重算到底发生了没有

抢占的教科书代价是"被踢的请求要从头重算 prefill"。这一轮有 38 次抢占, 按每条 6,200~8,200 token 算,应该多出二三十万 token 的白干活。 结果两个计数器给出了完全相反的答案:算力账多出近三成,token 账却一个字没记。 

# 计数器 A:iteration_tokens_total_sum(调度器记的 token 账)
实测总量 1,048,576 token
理论下限 128 × (6144 + 2048) = 1,048,576 token
差额 0  ← 一个 token 不多不少,精确停在理论下限上

# 计数器 B:estimated_flops_per_gpu_total(算力账)
实测 1.9884e16 FLOP
模型 1.5395e16 FLOP   ← 用长度扫描 5 个零抢占数据点标定
差额 +4.489e15 FLOP = +29.2%

# 把差额换算回 prefill token
4.489e15 ÷ 14.77 GFLOP/token = ≈ 30.4 万 token
30.4 万 ÷ 38 次 = 7,997 token / 次

# 独立校验:抢占时释放的 KV
38 次 × 6,242 token = 23.7 万 token   ← 与上面同量级

结论:重算发生了,但调度器的 token 计数器没记

两条独立证据(FLOPs 差额 30.4 万 token、抢占释放的 KV 23.7 万 token)互相印证, 重算量约 24–30 万 token,相当于 prefill 工作量多做了 30%–39%。 而 iteration_tokens_total 记下的是 1,048,576 —— 精确等于 128 × 8192 这个理论下限,一个 token 都没多。

实际代价没有想象中大:30 万 token 的 prefill 按实测 146 TF/s 算约 31 秒,占全程 492 秒的 6.2%。 真正让吞吐掉到 38% 的不是重算,是并发被 KV 池砍到了 16 条。 重算是伤口,并发塌缩才是断崖。

这个矛盾在两台不同的机器上原样重现,基本可以排除偶然。 在源码层面确认之前,不要把 iteration_tokens_total 当作"GPU 实际算了多少"的依据 —— 在有抢占的场景下它会系统性低报。

解码阶段被偷走的 27%

单条请求的解码阶段实测 65.61 秒,而 2047 个 token × ITL 中位数 23.39 ms 只需要 47.9 秒。 差出来的 17.7 秒(27%)就是被别人的 prefill、别人的重算、 以及自己被抢占后的空档吃掉的。

下一步这轮之后该做的五件事

  • 把 --max-num-seqs 设成真实容量,而不是 128。 本轮 --max-num-seqs 128 允许调度器放进 18–19 条,然后靠抢占再踢回 15–16 条 —— 38 次抢占全部是这个"放多了再踢"造成的。按日志的 14.66x 把它设成 --max-num-seqs 14,理论上抢占会降到 0,吞吐不变但 ITL 尾部更干净。 这是最容易验证、收益最直接的一条。 注意这个值跟着机器走:第一轮该设 10,这一轮该设 14。
  • 加上服务端前置队列长度上限。 本轮那 48 条排了两分钟以上的请求占着 HTTP 连接和客户端超时预算, 对吞吐却毫无贡献 —— 让超出的请求快速失败(429)更有用。 这是上一条的配套:--max-num-seqs 管驻留,队列上限管积压。
  • 补一组 p99.9 / p99.99 的 ITL。把 --metric-percentiles 改成 50,90,99,99.9,99.99 重跑一次, 应该能直接看到那 38 个巨大间隔的量级。
  • 在源码层面确认 iteration_tokens_total 的记录点。 两轮都出现了同一个矛盾:token 账等于(甚至略低于)理论下限,FLOPs 账多出 26%–28%。 两台机器复现,已经不是偶然。在确认之前,涉及抢占的场景下 MFU / 算术强度这类指标 都应该以 FLOPs 计数器为准。
  • 把"池子大小 → 驻留数 → 吞吐"做成真正的实验。 上一节那组两轮对照的结论(池子 +38% 只换来吞吐 +21%)值得信,但证据是捡来的, 不是设计出来的。用 --kv-cache-memory 把池子显式钉成 4 / 6 / 8 GiB 三档, 同一形状各压一次,就能把这条曲线直接画出来 —— 顺便还能验证"抢占频率与池子大小无关"这个更强的说法。

口径提醒

本轮只有 128 条请求、单次运行,没有重复测量;p99 相当于第 126–127 条, 而 TTFT 的分布主要由客户端的发压顺序决定(先发的排队短、后发的排队长), 所以 ttft p50 = 169 s 应理解为"批次中位数",不是稳态尾延迟。 要量稳态,需要改成固定到达率(--request-rate)而不是固定并发。

还有一处:和第一轮的对照不是严格的 A/B。 两轮的 KV 池差异来自驱动 / CUDA 版本和显存 profiling 的随机性, 不是人为设定的自变量 —— 第一轮内部换一次服务端启动,池子就从 86,896 变成了 86,864。 所以本报告里所有"第一轮 vs 第二轮"的对照,应当读作 "两个池子大小下各观察到一次",而不是"控制变量实验"。 要把它坐实,就是上面第五条那个实验。
