三个最容易混的地方

1 · TPOT 和 ITL 均值是同一件事的两种算法。 TPOT 是"每条请求先算自己的平均,再对请求取中位数";ITL 均值是"把所有间隔倒在一起平均"。 负载均匀时两者几乎相等(本轮 C=1 都是 15.83 ms), 有长尾时会分开 —— 两者一分开,就说明存在少数被拖长的间隔。

2 · 看 p50 得不出任何关于抖动的结论。 一次 200 ms 的停顿混在 25 万个间隔里,对中位数毫无影响,对均值影响也很小。 本系列反复出现的一条经验:抖动只在 p99 上露头; 而抢占这种更稀有的事件(万分之一量级)连 p99 都够不着,只能看专门的计数器。

3 · 吞吐不是 1 / TPOT。 TPOT 是单条请求的出字速度,吞吐是整台机器的产能 —— 后者约等于前者乘以并行的请求条数。 并发提高时 TPOT 会变差而吞吐会变好,这正是压测要权衡的那个交换。

结论线性得几乎没有误差

KV 占用随输入长度的增长,五个点全部落在一条直线上,R² = 0.99993。 斜率实测 15.99 —— 理论值是 16.00(并发数),偏差 0.045%。 这条直线的每一个系数都能从模型结构算出来,没有留下任何需要解释的余量。

这条线为什么值得亲手量一遍

容量规划的全部内容就是这条直线。给定 KV 池 P、平均上下文 L+O, 并发上限就是 P ÷ (L+O),没有第二个变量。 本轮 L=4096 时上限是 27 条 —— 而启动参数写的是 --max-num-seqs 128, 名义值比真实值大 4.6 倍。

注意这个 27 是这台机器的数。第一轮同样的算法给出 20 条, 因为那台机器的池子只有 4.64 GiB。斜率是模型的性质,截距是机器的性质 —— 前者可以跨机器搬,后者必须现读日志。

波形502 秒全程实况

五段测试连在一起看,KV 曲线是五级台阶,每一级都比上一级高得更多 —— 因为横轴的长度是翻倍的。 台阶顶部的锯齿是请求批次的换手:所有请求长度相同且 --ignore-eos, 它们几乎同时结束,腾出的槽位要等下一批 prefill 完才重新填满。

Waiting 队列的两副面孔

L=256 时 Waiting 恒为 0;L=512 与 L=1024 只有开场 1 秒有 9 / 5 条在等; L=4096 开场 6 秒里 Waiting 从 12 一路降到 0 —— 因为 chunked prefill 每步只能塞进有限的 token, 16 条 4K 请求要排队进场。p99 TTFT = 6.03 s 几乎全部来自这 6 秒。

这一轮的关键对照是:L=4096 稳态时 KV 只有 52%–58%, 离池子满还差一大截 —— 卡住新请求的不是显存,是调度器每步的 token 预算。 第一轮同一段测试 KV 已经到 80%,当时无法把这两个原因分开; 这一轮池子大了 38%,现象一模一样,结论就干净了。 全程 preempt 出现 0 次,没有任何请求被踢出重算。

排队首字延迟里,只有两成在算

这是本轮最想回答的问题。把 TTFT 拆成三段:排队(request_queue_time)、 prefill(request_prefill_time)、以及剩下的前端开销(分词 + HTTP + 首 token 送达)。 再把同轮 C=1 的单流测量放进来作参照 —— 那才是"纯计算"的下限。

同一段 prefill,并发下的墙钟贵了 3.9 倍

最干净的一组对照:同样是 1024 个 token 的 prefill,同轮 C=1 时服务端量到 93.5 ms, 本节 C=16 时量到 360.5 ms。同一段计算、同一张卡,墙钟慢了 3.9 倍。 多出来的 267 ms 不是排队(排队只有 47 ms),而是 enable_chunked_prefill 下, 这段 prefill 被切成块、混进 16 条正在解码的批次里,一块一块挤着算完的。 第一轮这个倍数是 3.9,这一轮还是 3.9。

这就是"排队贡献了多少"的答案

把并发扫描的单请求 TTFT 和本节叠在一起,517.0 ms 的平均首字延迟拆成四份。 注意下面这四个百分比是扣掉 C=1 同名基线之后的口径, 与上表「占 C=16 原始比」那一列不是一回事:

真正的 prefill 计算 18%(93.5 ms,C=1 实测,不可压缩)· 排队 9%(46.8 − 0.0 = 46.8 ms)· prefill 被抢步 52%(360.5 − 93.5 = 267.0 ms)· 前端开销放大 20%(109.7 − 8.8 = 100.9 ms)。 余下的 1.7% 是单流本身就有的 8.8 ms 前端开销,四段加基线正好合成 517.0 ms。

换个分母结论一样:并发带来的增量是 414.7 ms,其中排队占 11.3%、 prefill 被抢步占 64.4%、前端放大占 24.3% —— 无论怎么切, 被抢步的 prefill 都是最大的一块。 (第一轮的同一组数是 11.5 / 64.9 / 23.7,三位数字全部复现。)

结论是:在 C=16 这种很普通的并发下,TTFT 已经基本是一个调度指标, 而不是一个算力指标 —— 想压 TTFT,该动的是调度器的单步预算而不是换卡。 那个参数具体是什么、本轮它的值是多少,见本节末尾。

中位数涨 3.5 倍,尾部涨 15 倍

上面那张分解图画的是平均值。换成分位数看,长度轴上同样是尾部先塌 —— 而且塌的原因和并发轴一模一样:排队。 

# L 从 256 拉到 4096(16 倍)
TTFT p50     297.5 →  1047.4 ms       3.5×
TTFT p99     390.3 →  6027.1 ms      15.4×   ← 尾部涨得远比中位数快

# 拆开看是哪一段在涨
排队           1.5 →   318.5 ms      212×
prefill      229.4 →   804.4 ms       3.5×   ← 和 p50 同速,它不是尾部的原因

一条 4096 token 的请求正在做 prefill 时,后面排队的那条要等它把一批 chunk 走完才轮得到 —— 长 prefill 之间会互相阻塞。所以排队时间涨了 212 倍,而 prefill 本身只涨 3.5 倍, 和上一段"TTFT 是调度指标"是同一件事的两种量法。

这条尾部曲线可以直接当选型工具用

如果业务方给的 SLO 是「p99 TTFT < 2 秒」,那么在 C=16 这个运行点上, 输入长度的红线落在 1024 与 2048 之间 —— L=1024 时 p99 = 1.45 s,还有余量;L=2048 时已经 2.97 s,超了。 注意这条线是并发与长度的联合约束:降并发能把它往右推, 本报告只固定在 C=16 量了一条。

那 --max-num-batched-tokens 到底是什么

它是 vLLM 调度器的单步 token 预算 —— 每一次 forward(一个 engine step)里, 允许放进这一批的 token 总数上限。上面反复出现的"抢步""混批",全都由这一个数控制。 

# 一个 engine step 的 batch 是拼出来的
  decode token    每条正在生成的请求各贡献 1 个
+ prefill chunk   新请求的 prompt 被切块,塞进来 一块
  ─────────────────────────────────────────────
= iteration_tokens   ≤  --max-num-batched-tokens

# 采样脚本里那一列量的正是这个和。本轮 C=16 各长度点的实测:
  L=256   每步 30.3 个 token   其中 decode 16、prefill ≈ 14
  L=1024  每步 76.5 个 token   其中 decode 16、prefill ≈ 60
  L=4096  每步 265.1 个 token  其中 decode 15、prefill ≈ 250

# 注意这是【平均】。真正决定 ITL 尾部的是【单步峰值】,见下。

它为什么是 ITL 的旋钮:这个数决定了一个正在解码的请求,每一步要陪别人算多少 prefill。

  • 调大 → prefill 块更大 → 一个 prompt 用更少的 step 就算完 → TTFT 变好;但每个 step 变长,解码方向被拖住 → ITL p99 变差。
  • 调小 → 反过来:ITL 尖峰变矮,TTFT 变差。

这正是本节结论指向的那个交换。而显存这条退路已经在上一节排除了 (L=4096 稳态 KV 只有 52%–58%),能动的就只剩这个预算。

反推:本轮的预算很可能是 2048

这个值没有打进服务端日志(日志只给了 max_num_seqs 128 和 max_model_len 8192),但可以从 ITL 的尾部反推出来。 思路是:一次 ITL 尖峰,就是那一步顺带算了一大块 prefill, 多出来的时间除以 prefill 的实测算力,就是那一块有多大。

六个场景全部落在 2,000 上下

长度轴和并发轴是两组完全不同的负载,却给出同一个数 —— 单步 prefill 块被 2048 卡住了。 L=512 那一行只有 437,因为那时 prompt 太短、凑不满一整块。

这也顺带解释了后面 Figure 10 里那个现象:p99 ITL 稳定在 200 ms 左右, 不随长度继续涨。块大小被预算钉死了,长输入涨的只是块出现的频率,不是块本身。

这个预测足够具体:对上了就说明"ITL 尾部 = 单步 prefill 块"这个模型成立, 对不上就说明还有别的东西在制造那 200 ms。 顺带也能验证反推出来的 2048 对不对 —— 如果显式设 2048 之后 p99 不变,就坐实了。

物理一张卡,两种完全不同的机器

--enable-mfu-metrics 打开后,/metrics 会多出 estimated_flops_per_gpu_total 与 estimated_read_bytes_per_gpu_total 两个累积计数器,采样脚本每秒抓一次。名字里的 estimated 是实打实的 —— 它是 vLLM 按模型结构和当步调度到的 token 数推出来的,不是 GPU 性能计数器, 因此不含 kernel launch、padding 这类实际损耗。 把这两条按秒画出来,会看到一个很干脆的现象:同一张 4090, 在"纯解码"的那一秒和"正在 prefill"的那一秒,算力相差 一个数量级。

这两个比值到底是什么

一张 GPU 干活时有两堵墙:每秒能算多少次乘加,和每秒能从显存搬多少字节。 任何 kernel 都会先撞上其中一堵。MFU 与 MBU 就是分别量"离这两堵墙还有多远"的比值 —— 单看一个没什么用,放一起看才知道该往哪儿优化:MBU 高就去压显存流量 (量化权重、加大 batch、缩 KV),MFU 高就去换更好的 kernel 或更低的精度。

MFU 这个叫法来自 Google 的 PaLM 论文,它区分 MFU(只算模型本身必需的 FLOPs) 与 HFU(含重计算等硬件真正执行的)。本节全部是 MFU 口径。 

# 分子 —— 采样脚本每秒抓的两个单调累积量,分析时做窗口首尾差分 ÷ 窗口时长
estimated_flops_per_gpu_total       →  CSV 的 flops 列
estimated_read_bytes_per_gpu_total  →  CSV 的 read_bytes 列

              + 16 × L × 56 KiB             批内所有请求的 KV

# 第二条可以当场验证(L=256)

反向走的原因:算术强度

真正在动的量是算术强度(arithmetic intensity)—— 每从显存搬一个字节,能顺带算多少次浮点。 它低于脊点就是带宽受限,高于就是算力受限。 4090 的脊点 = 165.2 TF/s ÷ 1,008 GB/s = 163.9 FLOP/byte。

输入长度算术强度÷ 脊点MFUMBU

L = 2048118.20.72 ×40.9%56.7%

 算术强度 = Δflops ÷ Δread_bytes,单位 FLOP/byte。「÷ 脊点」这一列同时也就是 MFU ÷ MBU(0.174 / 0.267 / 0.410 / 0.721 / 1.218)—— 原因见下方恒等式。 
# 这不是巧合,是一个恒等式
MFU ÷ MBU = (FLOPs ÷ bytes) ÷ (峰值算力 ÷ 峰值带宽) = 算术强度 ÷ 脊点

# 所以「两条线交叉」和「算术强度穿过脊点」是同一件事

# 但分相来看,负载从来没有停在脊点上:
单个 decode 步    209 GFLOP ÷ 14.5 GB  = 12 ~ 15 FLOP/byte      远低于 163.9,深度带宽受限
一段 prefill      L × 13.05 GFLOP ÷ 14.14 GB
                  L=256   → 236 FLOP/byte
                  L=4096  → 3,780 FLOP/byte                远高于 163.9,深度算力受限

换句话说:把 prompt 拉长,没有让任何一个 kernel 变得更"算力密集" —— decode 步的强度甚至还从 14.8 掉到了 11.9(KV 读得更多)。 变的只是算力密集的 prefill 在时间轴上占了更大比例,于是平均强度被抬过了脊点。

四个别踩的坑

1 · estimated_ 不是硬件计数器。 它按模型结构和当步调度到的 token 数推算,不含 kernel launch 开销、CUDA graph padding, 也不含 softmax / LayerNorm / RoPE / 采样这些非 GEMM 算子。 好处是它跟着调度器走;坏处是它系统性地偏"干净"。

2 · read_bytes 只数读,不数写。 KV 写入、激活写回都没算进去,所以这里的 MBU 是下界 —— 真实的带宽占用比 82.1% 还要高。

3 · 分母是规格书数字。Boost 频率、不降频、无其它开销。 本轮按秒采样里有点算出 169.2 TF/s = 102.4% MFU —— 能超过 100%,就说明这对分子分母的精度大约在 ±5%,别读第三位有效数字。

4 · 分相看才有意义。纯 decode 的 MFU 恒在 8.4% 上下,看它没用, 那些秒该看 MBU;纯 prefill 的 MBU 只有百分之十几,该看 MFU(实测 88%–102%)。 整段窗口的平均值只适合回答"这段负载的配比是什么", 不适合回答"我的 kernel 写得好不好"。

带宽每一步都要把整个模型重读一遍

显存读字节这条计数器可以完整对上账。每个 decode step 要读两样东西: 全部权重(14.14 GB,与 batch 无关),以及批内所有请求的 KV(= 16 × L × 56 KiB,随 L 线性增长)。 把这两项按实测迭代率乘出来,和 read_bytes 的实测速率对照:

ITL 的斜率,是 56 KiB/token 的第二次独立验证

第一次验证靠的是容量(KV 占用计数器)。第二次完全不看计数器,只看时间: 单步 decode 的中位耗时随上下文线性增长,而这个斜率应该恰好等于 "多读的 KV 字节 ÷ 显存带宽"。 

# 实测线性拟合(5 个点,R² = 0.99989)
ITL_p50(L) = 16.23 ms + 0.00098 ms/token · L

# 理论:每步多读的 KV = 16 条 × 1 token × 56 KiB
16 × 57,344 B ÷ 1,008 GB/s = 0.00091 ms/token

# 吻合度
0.00091 ÷ 0.00098 = 93%  ← KV 读取跑到了显存带宽峰值的 93%(第一轮 92%)

把斜率换成绝对值:每个长度点的解码地板

上面验的是斜率(每多一个 token 多花多少时间)。同一个模型也能给出绝对值: 一步解码至少要把权重完整读一遍、再把批内所有请求的 KV 读一遍, 这些字节除以峰值带宽就是这一步的时间下限。

并发轴上的同一张账在《vllm-01-Qwen2.5-7B并发曲线》里:C 从 1 到 64,达成率从 89.0% 掉到 81.0%。 两条轴的达成率都在 80% 到 90% 这个带子里,但长度轴几乎是平的、并发轴掉了 8 个点 —— 因为加并发要多付调度和 kernel 效率,而拉长度只是让同一批权重多带几个 token。

代价吞吐的分叉

长度这个轴上有一个容易踩的坑:总 token 吞吐一路上涨,看起来机器越用越好; 但用户真正拿到的输出 token 吞吐一路下跌。两条线朝相反方向走。

但每个输入 token 的成本,是一路下降的

输出吞吐跌了 60%,不等于"处理输入"这件事变贵了。把 prefill 耗时除以输入长度, 得到的单位成本一路走低 —— 方向和输出吞吐正好相反。 

# prefill 墙钟 ÷ 输入长度
  L=256    229.4 ms ÷  256 = 0.896 ms / 输入 token
  L=512    281.7 ms ÷  512 = 0.550
  L=1024   360.5 ms ÷ 1024 = 0.352
  L=2048   547.1 ms ÷ 2048 = 0.267
  L=4096   804.4 ms ÷ 4096 = 0.196   ← 比 L=256 便宜 4.6 倍

原因就是上一节那条 roofline:prefill 是算力密集的,一次前向把 14.14 GB 权重读一遍, 能摊给 4096 个 token,而不是只摊给 256 个。 所以把多个短请求拼成一个长请求,往往比分开发更划算。

但这只降低了单位成本,没降低总成本

同一批数据里,TTFT p50 仍然从 298 ms 涨到 1047 ms —— 用户还是要多等。 "每 token 更便宜"是给运营看的账,"首字更慢"是给用户看的账,两本账方向相反。 拼请求之前先确认你优化的是哪一本。

Figure 9 那个交点,是划分负载类型的线

输出吞吐与总吞吐两条线在 L≈512 附近交叉。左边是生成密集 —— GPU 大部分时间在出字,输出吞吐说了算;右边是处理密集 —— 大部分算力花在啃输入上。 RAG、长文摘要、代码库问答落在右半边;对话式、补全类负载落在左半边。 两边该盯的指标不同,该调的参数也不同。

对照同样的 KV 占用,输出吞吐差 3.9 倍

把两条轴放在同一张图上:并发轴(L=1024,C 从 1 到 64)和长度轴(C=16,L 从 256 到 4096)。 横轴统一成 KV 池占用 —— 也就是"这次请求吃掉了多少显存预算"。

KV 占用相近的点两两配对。两条轴均取自本轮(Round 2)。

KV 占用是成本指标,不是产出指标

C=64/L=1024 和 C=16/L=4096 吃掉的 KV 差不多(67.5% vs 57.8%),p99 TTFT 也差不多(5.92 s vs 6.03 s), 但输出吞吐差 3.9 倍(1,388 vs 359 tok/s)。 (这个 3.9 和第三节 prefill 墙钟那个 3.9 毫无关系,数值撞车纯属巧合。)原因很直白: 解码吞吐正比于批内序列条数,而 KV 占用正比于批内 token 总数。 长上下文用同样的显存,换来的是更少的并行解码流。

有意思的是总 token 吞吐反而接近(6,939 vs 6,109 tok/s)—— GPU 干的活儿总量差不多, 区别只在于这些活儿有多少变成了用户看得见的输出。 这个 3.9 倍在第一轮也是 3.9 倍,尽管两轮的 KV 池差了 38%。

两轮测试在 L=1024 / C=16 上的吻合度

 c016 为 200 条请求的并发扫描点,len_1024 为 160 条请求的长度扫描点,采样与统计口径一致。最后一行 38.7% 的极差不是测量分歧 —— 两轮 KV 池分别是 86,896 与 120,064 tok,同样的 20,480 个 token 占比自然不同;分子完全一致(20,485 vs 20,435,差 0.24%)。

换个横轴,两条轴就重合了

上面那张图说的是"KV 占用预测不了产出"。但这两条轴并非没有共同语言 —— 只要把横轴换成一次迭代里参与计算的 token 总数 (就是 --max-num-batched-tokens 那一节量的 iteration_tokens), 它们的利用率曲线会叠在一起。

真正的自变量既不是并发数,也不是序列长度

是每步 token 数。C=64 × 1,152 和 C=16 × 4,224 的 tok/iter 分别是 311.6 和 265.1,落在同一个区间 —— 利用率也就落在同一个位置 (MBU 43.2% vs 43.6%)。这解释了一件事:为什么 《vllm-01-Qwen2.5-7B并发曲线》Figure 4 那张"两堵墙"和本报告 Figure 6 长得几乎一样。 它们画的本来就是同一条曲线,只是从两条不同的路走上去的。

实用含义:想估一个没测过的配置落在哪堵墙上,不用管它是"高并发短上下文" 还是"低并发长上下文",先把 tok/iter 算出来,再到这条曲线上查。 两条轴唯一分家的地方在产出侧 —— 同样的 tok/iter,并发轴换来更多输出 token, 这正是上一段那 3.9 倍。

这批数据能不能信:四条自检

  • 零失败、零抢占:800 条请求全部成功,KV 峰值只到 57.8% —— 这一轮测的是纯粹的长度效应,没有混进抢占的影响(那是 Test 4 的事)。
  • 每请求输出 token 精确等于 256,五档全部如此,--ignore-eos 生效。 各档工作量在输出侧完全一致,差异只可能来自输入。
  • 只变了一个变量:服务端全程没重启,并发固定 16、输出固定 256、每档 160 条请求, 只有 --random-input-len 在变。
  • 每档换了 seed(seed = 输入长度),档间没有 prompt 重复; vLLM 侧 enable_prefix_caching: False 全程关闭 —— 五个点之间不存在缓存命中。

一处需要注意的口径:表里的 prefill 是墙钟,不是纯计算

prefill 这一列取自服务端 request_prefill_time 直方图, 量的是"这条请求的 prefill 从开始到结束经过了多少时间"。 开了 chunked prefill 之后,一条请求的 prefill 会被切片、和别人的 decode 交错执行, 所以这个数字里含有"等待被调度"的成分 —— 本报告第三节那 267 ms 的"抢步"正是从它里面拆出来的。 要拿它算纯 prefill 算力,得用 Figure 5 的分相曲线或 FLOPs 计数器交叉验证,别直接除。

下一步这轮暴露出来的四个口子

  • L=512 那一点要重测(采样漏峰顶,见 Figure 1 注)—— 拟合斜率里 0.045% 的偏差基本都来自它。把采样提到 5 Hz,或把每个长度点跑得更久些。
  • 补一个 L=8192 的点。本轮 L=4096 时 KV 才 57.8%, 而 MFU/MBU 的交叉点算出来在 L≈3,157 —— 交叉点右边只有一个测量点,外推没有底气。 L=8192 需要 16×8448 = 135,168 tok,正好超过池子, 顺便还能第一次看到 preemption。
  • 把"抢步"这一项单独量出来。本轮的 267 ms 是靠 C=1 基线相减得到的差值, 不是直接测量。调低 --max-num-batched-tokens 重跑, 看它是否随块大小线性缩小,才能确认因果。
  • read_bytes 的残差值得追。二项模型系统性低估 2%–7%, 且随 L 单调增大。如果确认是 prefill 激活读写,可以加第三项 激活 ≈ α × prefill_tokens 拟合出 α,把这本账彻底做平。
