结论三句话

这不是"谁更好",是两条不同的取舍曲线 —— 而且它们在一个很低的位置就交叉了。

真正的分界线不是并发数,是延迟预算

p99 TTFT ≈ 730 ms

按吞吐算,两条曲线在 C ≈ 8.3 换位。但生产上并发不是自己选的, 是被 SLO 反推出来的 —— 换成"你能忍受多少首字延迟"做横轴, 分界点落在 p99 ≈ 730 ms:比这紧,llama.cpp 赢;比这松,vLLM 赢。

  • 量化省下的字节,在单流上原样兑现。 每步要读的权重 14.14 GB → 4.68 GB,解码步长 15.83 ms → 5.84 ms(2.71×)。 字节数本身能对上 vLLM 的 read_bytes 计数器,误差 1.2%。
  • 但"摊薄字节"的能力没有被兑现。 并发 1→64,vLLM 的解码步长只涨 42%,llama.cpp 涨 505%。 批处理的全部价值就是"权重读一次、喂给一批",这件事 llama.cpp 基本没做到。
  • 量化真正稳赚的是显存。 同一张卡,llama.cpp 的 KV 池是 262,144 token,vLLM 是 120,064 —— 2.18 倍。 对长文档、多轮对话这类 KV 吃紧的场景,这个价值超过解码速度。

指标量的是什么为什么这份报告需要它
TTFT从发出请求到收到第一个 token用户点下回车后的"卡顿感"。SLO 通常定在它的 p99 上,本报告的选型分界线就画在这条轴上。
ITL相邻两个输出 token 的间隔出字的流畅度。它正常而 TTFT 爆炸,说明是排队;它也慢,说明是解码本身有问题 —— 两种病。
SLO事先定下的延迟承诺例如"p99 TTFT ≤ 1 秒"。有它才能把"该开多大并发"变成一个可计算的问题。
MFU / MBU算力 / 带宽跑到峰值的百分之多少判断瓶颈在哪堵墙上。解码是访存密集(看 MBU),prefill 是算力密集(看 MFU)。

选型先定延迟预算,再反推并发

"交叉点 C≈8"这个说法有个隐含假设:你可以自由选择并发。 但生产上并发是被 SLO 反推出来的 —— 先定"p99 首字延迟不能超过 X", 再看这张卡在这条线下最多能接多少并发。换个 SLO,结论就翻面。

同一份硬件、同一个模型,结论在 500 ms 和 2000 ms 之间翻了个面。 任何"A 引擎比 B 引擎快 N 倍"的说法,不说清延迟约束就是没有意义的。

直觉解释:SLO 越紧 → 允许的并发越低 → 越接近单流 → 量化的带宽红利占主导; SLO 越松 → 并发越高 → 越依赖批处理效率 → vLLM 的调度优势占主导。

什么时候该用 llama.cpp

单人 / 低并发(C ≤ 8)、边缘设备、显存吃紧但要长上下文、 或者延迟 SLO 非常紧(p99 < 500 ms)。 它在这些场景不是"凑合",是更优解 —— 单流快 2.6 倍、每一档 TTFT 都更低、KV 容量还多一倍。

什么时候该用 vLLM

多租户在线服务、并发 > 10、要用 SLO 做容量承诺、 需要抢占 / 排队而不是失败的降级行为。 并发一过 8,批处理效率就成了唯一重要的事 —— 而这一项两边差 3 倍以上,且差距随并发继续扩大。

机制为什么会这样

上面那张表里,llama.cpp 赢的全是"单条请求"的项,vLLM 赢的全是"一批请求"的项。 这不是巧合 —— 背后是两条独立的机制。

机制一:prefill 和 decode 是两种完全不同的负载

decode 是访存密集的:生成一个 token 要把整个模型权重读一遍, 量化把这堆字节压小,步长就按同样比例变短。 prefill 是算力密集的:一次前向处理上千个 token,权重读一次摊给所有 token —— 瓶颈在 FLOPs 不在带宽,而 Q4_K 的解量化只会让 FLOPs 更多。 

# 同一颗芯片,瓶颈随批量大小在两堵墙之间移动(vLLM 计数器实测)
C=1    MBU 88.0%   MFU  2.5%    ← 贴着访存墙,算力几乎闲置
C=64   MBU 43.2%   MFU 57.3%    ← 反过来了,交点在 C≈44

# 长度扫描把并发钉死、只拉输入长度,走到了同一个地方
L=256  MBU 82.1%   MFU 14.3%
L=4096 MBU 43.6%   MFU 53.1%

# 真正的自变量既不是并发也不是长度,而是"一次迭代里参与计算的 token 总数"
# 两条轴按 tok/iter 对齐后,MFU 逐点差 <0.7 pt、MBU <3.6 pt

推论:量化收益随负载形状变化

量化换来的是解码速度和显存,不是首字延迟 —— 服务端量到的纯 prefill llama.cpp 85.3 ms vs vLLM 93.5 ms,只快 9%,而且这 9% 来自实现细节不是位宽。 所以:对话类负载(短输入长输出)量化收益大; RAG / 长文摘要(长输入短输出)收益小得多。

机制二:省字节是一次性红利,摊薄字节才可复利

批处理的原理是:一个解码步把权重读一次,同时喂给 C 条序列 —— C 越大, 每个 token 分摊到的权重字节越少。理论地板 (权重 + C × 单条KV) / 带宽 随 C 增长得非常慢。拿实测除以这个地板,就得到"批处理红利吃到了多少"。 

# 每多接一条并发,解码步长要多付多少
理论地板   单条 KV ÷ 带宽                   = 0.066 ms / 条
vLLM       (22.50 − 15.83) ÷ 63             = 0.106 ms   ← 地板的 1.6 倍
llama.cpp  (35.32 −  5.84) ÷ 63             = 0.468 ms   ← 地板的 7.1 倍

llama.cpp 的批量解码,更像是"把单流做了 C 遍"

如果批处理真的只多读 KV,边际成本应该贴着 0.066 ms。 vLLM 的 0.106 说明它基本吃到了红利;llama.cpp 的 0.468 是地板的 7.1 倍, 意味着权重每步被重复读、重复解量化的成分很大。 这解释了全部现象:C=1 时每步字节少 3 倍 → 赢; C 变大后 vLLM 把自己那 14.14 GB 摊薄了 64 次,llama.cpp 几乎没摊薄自己的 4.68 GB → 输。

直接证据在《llama-cpp-压测》里:CUDA graph 复用率从 99.2% 崩到 0%, 与达成率的塌陷同步发生。相关性极强,但因果还需要 -DGGML_CUDA_USE_GRAPHS=OFF 的对照实验才能闭合。

容量能算出来,不用压测

上面两条机制决定"跑多快",这一条决定"能跑多少"。 好消息是:它是全篇唯一一个纯算术的部分 —— 精确到不需要压测。 

# 每 token 的 KV 字节,完全由模型结构决定
2 (K,V) × 28 层 × 4 KV head × 128 dim × 2 B = 56.0 KiB   GQA 让它比 MHA 小 7 倍

# 于是容量红线是一道除法
单请求占满 8,192 上下文 = 8192 × 56 KiB = 448 MiB
vLLM 池子 6.41 GiB ÷ 448 MiB           = 14.65 条

# 压爆那一轮的实测:驻留均值 15.65 条,比预告高 5%
# (因为请求刚进来只占 6144 token,要解码 2048 步才涨到 8192)
# 第一轮同样是 11.17 vs 10.60 —— 两台机器,同一个 +5% 偏差率

压爆不等于崩溃 —— 这是 PagedAttention 的价值

超卖 4.4 倍、KV 顶到 100%、抢占 38 次,结果是零失败、零错误、输出 token 一个不少, 只是排队排了 169 秒。这是一个把硬失败转化成软降级的设计。

而且这个组合本身就是诊断结论:ITL 正常 + TTFT 爆炸 = 容量不够,在排队 (加卡、减并发、缩短 max_model_len 都能救); ITL 也慢 = 解码本身有问题(要查 batch 配置、kernel、量化实现)。 前者是《vllm-04-断崖》里 vLLM 的病,后者是《llama-cpp-压测》里 llama.cpp 的病。两种病,两种药。

落地如果你要在生产上跑它

  • 先定 SLO,再反推并发,不要先定并发。 本轮数据显示,p99 TTFT 从 500 ms 放宽到 2000 ms,最优引擎会换人。 把"p99 TTFT < X"写进配置文档,比写"max-num-seqs = N"有意义得多。
  • 容量红线抄启动日志那一行。 vLLM 的 Maximum concurrency for N tokens per request: M 是用 KV池 ÷ max_model_len 算的,两轮实测都只比它高 5%。 不需要压测就能做容量规划,压测只用来标定。
  • 缩短 --max-model-len 比加卡便宜。 容量红线与它成反比:8192 → 4096 直接把可驻留请求数翻倍。 多数业务的真实上下文远小于配置值。
  • 监控只盯三个指标。 ITL p50(解码健不健康)、waiting 队列长度(容量够不够)、 num_preemptions_total(有没有在做无用重算)。 TTFT 是结果不是原因,看它诊断不出问题。 顺带一提:p99 ITL 看不见抢占 —— 38 次抢占混在 26 万个间隔里只占 0.0145%, 落在 p99.99 上。
  • 过载时唯一有效的手段是限流,不是加速。 压爆那一轮里用户等的 169 秒,有 168 秒在等前面的人,prefill 本身只要 1.10 秒 —— 换一张 H100 也只会让那一秒变成半秒。 在服务端设并发上限并对超出的请求快速失败(429),比让它们排 169 秒有用得多。
  • 把 --max-num-seqs 设成真实容量。 本轮设 128,调度器放进 18–19 条再靠抢占踢回 15–16 条 —— 38 次抢占全是这么来的。 按日志的 14.66x 设成 14,理论上抢占降到 0、吞吐不变、ITL 尾部更干净。 注意这个值跟着机器走。
  • 跨引擎对比必须客户端完全一致。 本轮用同一份 sweep.sh 打两个端口,并显式写死 --temperature 0、--random-range-ratio 0、每档独立 seed。 服务端的默认值是变量,不是常数。 但要注意"客户端一致"不等于"工作量一致":本轮 vLLM 七档每条精确 256 个输出 token, llama.cpp 是 250–256 不等,合计少 1.35% —— 吞吐是"输出 token ÷ 墙钟", 所以这张表把 llama.cpp 低估了约 1.35%(方向对它不利,但远小于 C≥16 时 20%–57% 的差距, 不改变任何结论)。跨引擎对比要核对实际输出 token 数, 不能假设 --ignore-eos 在两边行为一致。

诚实没搞清的、没测的

没搞清的

  • llama.cpp C=32 那一档的异常。 逐槽 16.3 tok/s,比并发翻倍的 C=64(28.3)还慢 —— 更多序列反而更快,说不通。 已排除显存、热节流、缓存;那 1 条失败请求反而是线索之一 —— 它与"该档每条输出 token 最少(250.00,七档最低)"、"CUDA graph 复用率归零"同时出现。 需要 -DGGML_CUDA_USE_GRAPHS=OFF 的对照实验。 在那之前,这一档不该写进任何结论 —— 本报告的交叉点用 C=8/16 算,批处理效率引用 C=64,都绕开了它; 唯一受影响的是 SLO 表 <2000 ms 那一行,已在上面标注。
  • CUDA graph 复用率与性能的因果关系。 相关性极强、机制上合理,但服务端日志没有解释原因(verbosity 已开到 3)。
  • 抢占场景下两个计数器打架。 iteration_tokens_total 精确等于理论下限 128 × 8192 = 1,048,576 —— 一个 token 都没多记; 而 FLOPs 计数器多出 29%。两台机器复现,已经不是偶然。 在源码层面确认之前,涉及抢占的场景下 MFU / 算术强度都应以 FLOPs 计数器为准。

没测的

  • KV 量化。两边的 KV 都是 FP16(刻意控制的变量)。 llama.cpp 的 -ctk q8_0 -ctv q8_0 能把它砍一半 —— 权重量化的红利随 batch 变小,KV 量化的红利随 batch 变大, 这是比权重量化更有意思的旋钮,也可能直接改写上面那张 SLO 表的右半边。
  • 池子大小的受控实验。两轮之间 KV 池差 38%(4.64 vs 6.41 GiB) 是驱动与显存 profiling 的意外,不是设计。应该用 --kv-cache-memory 显式设三档做真正的对照。
  • llama.cpp 的 -c 没有调平。 本轮给它开了 -np 64 -c 262144,KV 池按满配分配, 把量化省下的显存又吃回去了。设成等效容量再测一次,才能看到 Q4 真正的显存红利。
  • 多卡、投机解码、chunked prefill 调参、其他模型规模、-b/-ub 对停顿的影响。

一个被证伪的假设,也记在这里

第二轮重跑 vLLM 的动机是"第一轮的 repetition_penalty 1.05 让它偏悲观"。 结果七个档位的差异全在 ±1.2% 以内、方向还不一致 —— 这是噪声,假设错了。 但重跑不算白做:它把"采样参数不同构"从怀疑名单里划掉了, 剩下的差异只能归因于引擎本身。排除一个假设也是结果。详见《vllm-02-TTFT解剖》。
