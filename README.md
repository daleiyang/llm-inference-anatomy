# llm-inference-anatomy

**把大模型推理拆开看：从模型结构推出成本模型，再用压测验证它。**

大多数推理性能的仓库是「我跑了一堆 benchmark」。这个仓库反过来做：
**先从参数张量逐层算出该有的数，再上机器量，看两边对不对得上。**
对上了，这个数才敢拿去做容量规划；对不上，那个缺口本身就是发现。

第一阶段的例子 —— 手算 KV Cache 每 token 占用，与 vLLM 启动日志的实测值差 **0.03%**：

```
2 (K,V) × 28 层 × 4 KV头 × 128 dim × 2 B = 57,344 B = 56 KiB / token
6.41 GiB ÷ 56 KiB = 120,025 token        vLLM 日志实测 120,064 token
```

于是「这张卡能扛多少并发」变成一道除法，**不需要压测**。压测只用来标定。

## 目前的成果

### [01 · Decode Latency Anatomy](01-decode-latency-anatomy/) — 已完成

一张 RTX 4090 上把 Qwen2.5-7B 拆开量：**1 份逐层结构拆解 + 6 份压测报告**，
10 组压测、7,594 条请求、**两轮跨机器独立复现**，原始数据一条没删。

| | |
|---|---|
| **选型结论** | vLLM 与 llama.cpp 的分界线不是并发数，是延迟预算：**p99 TTFT ≈ 730 ms** |
| **容量结论** | KV 占用对输入长度线性，拟合斜率与理论值差 **0.045%**（R²=0.99993）—— 容量能算不用测 |
| **过载结论** | 超卖 KV 池 4.4 倍、抢占 38 次，结果**零失败**；抢占是稳定在 99.58% 的负反馈控制环 |
| **监控结论** | **p99 ITL 看不见抢占**（38 次混在 262,016 个间隔里 = 0.0145%），别拿它做告警指标 |
| **量化结论** | 量化省字节（单流 **2.71×**），省不了调度（C=64 批处理效率 **81% vs 25%**） |

## 贯穿始终的三条规矩

这套方法论是第一阶段跑完两轮之后定下来的，后续每个阶段都照此执行。

**一 · 先算，再测，然后对账。**
任何一个数在上机器之前，先从模型结构或硬件规格推一遍。
两边对上才写进结论；对不上就把缺口单独拎出来查 —— 第一阶段最有价值的几个发现都来自这里
（比如两个计数器对同一件事给出相反答案）。

**二 · 自检不过的数据不进报告。**
每轮跑完立刻查：输出 token 数是否精确等于设定值、采样参数是否真的生效、
缓存是否真的关着、失败请求数、抢占计数。第一阶段靠这条查出了
`--ignore-eos` 在 vLLM 与 llama.cpp 上**行为不一致**（工作量差 1.35%），
不查就会当成引擎性能差异写进结论。

**三 · 原始数据一条不删，结论必须可追溯。**
bench 原始 JSON、1 Hz 服务端采样 CSV、完整服务端日志、环境指纹，全部入库。
报告里每个数都能追回源文件 —— 包括那些后来被推翻的。

## 关于「诚实」这一节

每份报告最后都有一节叫**「没搞清的、没测的」**，写明哪些结论只是相关性、
哪些实验没做、哪个数不该被引用。第一阶段里就有一档数据被明确标注为
**「在补上对照实验之前，不写进任何结论」**。

这不是谦虚，是划定边界。**知道自己不知道什么，比多列几个结论更值钱。**
